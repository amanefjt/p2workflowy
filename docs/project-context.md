# p2workflowy V2: Project Context & Architecture Philosophy

このドキュメントは、p2workflowy V2開発における「設計の背景」「採用したアーキテクチャの理由」「過去の開発から得た暗黙のルール」をまとめたものです。実装エージェントは、PRD（指示書）に加えてこの設計思想を完全に理解し、遵守してください。

## 1. Core Philosophy (なぜこの設計にするのか)
LLMに「長文の構造化と翻訳」を丸投げすると、必ず段落の欠落、フォーマットの崩れ、幻覚（Hallucination）が発生します。
したがって、V2の絶対的な設計思想は**「テキストの分割・結合・フォーマット変換は必ずPythonの決定的（Deterministic）なプログラムで行い、LLMには『要約』と『チャンク単位の翻訳』という純粋なタスクのみを担当させる」**ことです。LLMの不確実性をプログラムのロジックで檻に閉じ込める設計にしてください。

## 2. Detailed Logic Requirements

### A. PDF Noise Handling (Smart Unwrap)
PDFから抽出したテキストには特有のノイズがあります。以下のヒューリスティックなルールをPythonロジックとして実装してください。
- **孤立行の削除**: 数字だけの行（ページ番号）や、極端に短く大文字始まりの孤立行（フッター等）は削除。
- **改行の結合（Smart Unwrap）**: ある行の末尾がピリオド(`.`)やコロン(`:`)、引用符(`"`)で終わっておらず、かつ次の行が小文字で始まっている場合、間に空行があっても「文の途中」とみなし、強制的に1つの段落として結合する。
- **単語の癒着（wordninja）**: `epicTheLordoftheRings` のようにスペースが欠落した異常に長い文字列は、旧コードの知見を活かして `wordninja` 等で可能な限り単語分割する。

### B. Glossary Handling (ハイブリッド辞書)
専門用語の翻訳ブレを防ぐための仕組みです。
- ユーザーが提供する `glossary.csv` がマスター（最優先）です。
- Phase 2 で LLM に論文全体から「重要キーワードと訳語のペア」を自動抽出させます。
- この2つをマージしますが、**キーが重複した場合は必ず `glossary.csv` の値を優先して上書き（オーバーライド）**してください。

### C. Translation Strategy (Sliding Window)
長文を直列で翻訳する際の「文脈の喪失」を防ぐための重要ロジックです。
- 翻訳APIを呼ぶ際、プロンプトには常に以下の3つをコンテキストとして動的に注入してください。
  1. Phase 2 で生成した「論文のレジュメ」
  2. B で生成した「マージ済み用語集」
  3. **直前に翻訳したチャンクの「原文と訳文」のペア（Sliding Window）**
- これにより、代名詞（it, they）の指す対象や、文体（だ・である調）の一貫性が保たれます。

### E. Performance Standard (Golden Rule)
Gemini 3 Flash の性能を最大化するための検証済みパラメータ（Golden Rule）です。これらを変更する際は、必ずベンチマーク測定を行ってください。
- **Schema-free**: `response_schema` は使用しない。APIペナルティ回避のため。
- **Concurrency**: `Semaphore(4)`。4並列を推奨。
- **Batching**: `MAX_BATCH_CHARS=6000`, `MAX_BATCH_CHUNKS=20`。
- **Fallback**: LLMの JSON 出力が Markdown ブロックで囲まれてもパースできるよう、正規表現による抽出を必須とする。

## 3. Legacy Code Treatment
旧リポジトリ（V1）のコードは、アーキテクチャレベルでは完全に「負債」です。
状態管理やデータの受け渡しフローなどの**「構造（Architecture）」は一切引き継がないでください。**
引き継ぐべきは、文字列操作、正規表現、`wordninja`の呼び出し方といった**「局所的なテキスト処理の知恵（泥臭いロジック）」のみ**です。
