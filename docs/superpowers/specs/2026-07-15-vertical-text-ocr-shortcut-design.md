# 調査+設計メモ: Mac標準機能による縦書き史料OCRショートカット

**日付**: 2026-07-15
**ステータス**: 設計確定・**実装は保留**（「今はやらない」との指示により、議論の記録として残す）
**位置づけ**: p2workflowy 本体（英語学術論文・書籍 → 日本語Workflowyアウトライン変換）とは**別軸のテーマ**。NDL OCR等で日本語縦書き史料を読み取る際の段落復元問題について、藤田氏との対話（別セッションのAIとのやりとり＋本セッションでのブレインストーミング）を素材に、実現可能性を調査し設計をまとめたもの。p2workflowyのリポジトリに置くのは、既存の `SpreadSplitter`（見開き分割ロジック）との関連づけがあるため、および同種の調査メモの置き場所として `docs/superpowers/specs/` の慣例に従うため。

---

## 1. 問題設定

NDL OCR（および軽量フォーク版）は日本語縦書きの文字認識精度自体は高いが、**画像上の行末で機械的に改行を入れる**ため、原文では連続しているはずの段落が行ごとにブツ切りのテキストになる。これは「文字認識（Vision/OCRエンジンの役割）」と「意味的な段落復元（言語理解の役割）」が別工程である以上、原理的に避けられない構造的limitationである。

## 2. 検討した選択肢とその整理

別セッションのAIとの対話で以下の順に選択肢を検討し、次の理由でそれぞれ却下・採用した。

| # | 選択肢 | 却下/採用理由 |
|---|---|---|
| 1 | ルールベース後処理（文末記号・行頭インデント判定の正規表現） | 誤字・ルビ混入・短い見出し行などで簡単に破綻する。決定論的で追跡可能という利点はあるが、実用精度が不足 |
| 2 | NDL OCR → 外部LLM API（Claude/GPT-4o）でテキストのみ後処理 | 一度ブツ切りにした時点で画像側の空間情報（インデント・段組配置）が失われており、ハルシネーションの温床になる |
| 3 | 画像を直接マルチモーダルLLM（Claude/GPT-4o Vision）に投入し、OCRと段落復元を一括処理 | 精度面では最有力。ただし外部クラウドAPIへの送信が前提になり、藤田氏の「ローカルファースト」方針（`~/.claude/CLAUDE.md`: corpus・個人データを不用意にクラウドへ送らない）に反する |
| 4 | Mac標準OCR（Live Text）+ Apple Intelligence Writing Toolsで後から整形 | 実質的に選択肢2と同じ二段階構造（テキスト化→文脈復元）で、空間情報の欠落問題は解消しない |
| 5 | サードパーティのローカルLLM（Ollama等）を導入して同様のパイプラインを自前構築 | 技術的には可能だが、追加インストールが必要で「Macを持つ人なら誰でも使える」という配布性の要件（藤田氏の意向）を満たさない |
| 6 | **Apple Foundation Models framework / Shortcutsアプリの「モデルを使用」で、画像を直接オンデバイスLLMに渡し一括処理** | **採用**。追加インストール一切不要、完全オンデバイス、ローカルファースト方針に合致、配布性も高い（Shortcutsはリンク1つで共有可能） |

選択肢6が成立するかどうかは、当初「Apple純正フレームワークはテキスト入力オンリーで画像を直接渡せない」という私（Claude、2026年1月時点の知識）の理解に基づき、**いったん「実現不可能」と判定した**。この判定は誤りだったことが後述の調査で判明した。

## 3. 訂正: 「WWDC 2026でマルチモーダル対応」は幻覚ではなく事実だった

会話の終盤、別セッションのAIが「Apple Foundation Models frameworkがWWDC2026でマルチモーダル対応し、Python SDK・`fm` CLIが提供された」と述べた際、私はこれを**幻覚（hallucination）と断定した**。理由は、私の学習データが2026年1月までであり、WWDC2026（例年6月開催）の内容を知り得ないため。

しかし本セッション内でWeb検索により一次情報（Apple公式ドメイン）を確認した結果、**この記述は事実だった**。

### 確認できた事実

- **Foundation Models framework は WWDC 2026（2026年6月8日）でマルチモーダル画像入力に対応**。`LanguageModelSession` に `.image()` コンテンツブロックが追加され、`UIImage`/`NSImage`/`CGImage`/Core Image/CVPixelBuffer/ファイルURLから画像添付が可能。Vision frameworkのOCR・バーコード読み取りツールをモデルが内部で直接呼び出せる（すべてオンデバイス）。
  出典: [WWDC26 Apple Intelligence guide](https://developer.apple.com/wwdc26/guides/apple-intelligence/), [What's new in the Foundation Models framework (WWDC26 session 241)](https://developer.apple.com/videos/play/wwdc2026/241/)
- **`fm` CLIとPython SDKも実在**。「Build AI-powered scripts with the fm CLI and Python SDK」というセッション（WWDC2026/334）が公開されている。
- **AFM 3 Core Advanced**（200億パラメータ、実行時は1〜4Bパラメータのみ活性化するスパースMoE構成、フルモデルはNANDフラッシュに格納しDRAM制約を回避）は "natively multimodal" と明記されている。
  出典: [Introducing the Third Generation of Apple Foundation Models](https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models)（Apple Machine Learning Research公式ブログ）
- 通常のAFM 3 Core（オンデバイス、密モデル、30億パラメータ）も同フレームワーク経由で画像入力を受け付ける。

### 追加確認: Xcode不要の「ショートカット」アプリでも画像入力が可能

Foundation Models frameworkはSwift API（開発者向け）だが、ノーコードの「ショートカット」アプリの**「モデルを使用」アクションは、iOS/macOS 26の時点ですでに写真を直接入力として渡せる**ことをApple公式ヘルプで確認した。

> 「テキスト入力には変数、前のアクションの出力、カレンダーイベント、リマインダー、写真などを含めることができる」

出典: [Use Apple Intelligence in Shortcuts on Mac](https://support.apple.com/guide/mac-help/use-apple-intelligence-in-shortcuts-mchl91750563/mac)（Apple公式サポート）

つまり、**Xcodeでのアプリ開発なしに、Shortcutsアプリだけで「画像→丸ごとLLM→段落復元済みテキスト」の一括処理が今すぐ組める**。当初「OS標準では封印されており、ボタン化されていない」と述べたのは古い（2026年1月以前の）状態の記述であり、2026年7月現在は誤り。

### 教訓

私自身の学習データのカットオフ（2026年1月）以降の情報について、「知らない」ことと「存在しない」ことを混同して断定してはならない。今回はWeb検索で一次情報を確認できたため訂正できたが、確認せずに「幻覚」と断じていれば誤った情報を採用させるところだった。

## 4. 確定した設計

ブレインストーミングで対話形式により以下を確定した。方針: **OCR単体を挟まず、画像をそのままオンデバイスマルチモーダルLLMに渡して段落復元済みテキストを一発で得る**（藤田氏の要望「丸ごとLLMでやりたい。テキストを寸断すると改行がわからなくなる」に対応）。

### 4.1 全体フロー

```
PDF選択
  ↓
①メニュー選択（本1冊につき1回）: 縦書き・1段組 / 縦書き・2段組 / 横書き・1段組 / 横書き・2段組
  → 対応する読み順プロンプト文を変数に確定
  ↓
②「PDFからイメージを取得」→ ページ画像の配列
  ↓
③各ページ画像をループ
   ├─ 「画像の詳細を取得」で 幅/高さ の比率を算出
   ├─ 比率 > 1.1 なら見開きと判定 → 「画像を切り抜く」で中点を左右2分割
   │    （縦書き選択時は右→左の順、横書き選択時は左→右の順で配列に追加）
   └─ 単ページならそのまま1枚を配列に追加
  ↓
④分割後の各ページ画像に対し「モデルを使用」（オンデバイス・画像添付・①のプロンプト）
   → 出力テキストを配列に累積
  ↓
⑤「テキストを結合」→「テキストファイルを作成」
   → 出力先: 元PDFと同じフォルダに `<PDFファイル名>.txt`（PDF1冊=1テキストファイル）
```

### 4.2 見開き自動判定・分割

`core/engine/p1_ingest/spread_splitter.py` の `SpreadSplitter` と同じ**アスペクト比閾値 1.1**（`SPREAD_ASPECT_THRESHOLD`）を判定基準として踏襲する。ただし実装はPython非依存の**ネイティブ「画像を切り抜く」で中点クロップ**とし、`SpreadSplitter._find_gutter_in_gray()` が行う輝度解析ベースのノド（綴じ目）検出は行わない（実装をPure Shortcutsに保ち、配布性を優先するトレードオフ。詳細は §5 決定ログ参照）。

### 4.3 プロンプト設計

書字方向×段組の4パターンで、共通制約（誤字修正・現代語訳をしない／行末改行ではなく文脈上の段落区切りでのみ改行）をベースに読み順の指示のみ差し替える。画像はそのまま「モデルを使用」に添付し、OCRを別アクションで挟まない。

### 4.4 モデル選択

**オンデバイスのみ**（Private Cloud Computeも不使用）。理由: `~/.claude/CLAUDE.md` の「ローカルファースト」方針（corpus・個人データを不用意にクラウドへ送らない）を史料画像にも適用。Private Cloud ComputeはAppleの暗号化クラウドで第三者送信はないが、それでも端末外に出る点を避ける判断。

## 5. 決定ログ（対話で確定した判断）

| 論点 | 決定 | 備考 |
|---|---|---|
| OCR前処理を挟むか | 挟まない（画像を直接LLMへ） | 段落断片化の根本原因を回避するため |
| 属性選択の粒度 | PDF1冊単位で一定 | 本全体で同一レイアウトという前提。ページ単位で変わる資料は本設計の対象外 |
| 見開き判定 | 自動判定（アスペクト比>1.1） | ユーザーに選ばせる軸から除外し、手動選択は「縦書き/横書き」「1段組/2段組」の2軸4パターンに圧縮 |
| 見開き分割の実装方式 | ピュアShortcuts（中点クロップ） | p2workflowyのSpreadSplitterのノド検出ロジックはPython/numpy依存のため不採用。「他人にリンク1本で配布できる」という配布性を精度よりも優先。後段がOCRでなくLLMの視覚推論のため、多少のクロップずれは許容範囲と想定（未検証） |
| 使用モデル | オンデバイスのみ | ローカルファースト方針。Private Cloud Computeも不使用 |
| 出力形式 | PDF1冊=1テキストファイル | ファイル名は元PDFと同名の `.txt`、保存先は元PDFと同じフォルダ |
| 入力ソース | PDFのみ | カメラ撮影・都度OCRは対象外 |

## 6. 未検証のリスク（実機テストが必要）

- オンデバイスモデル（AFM 3 Core, 3B）は近代文語・崩し字混じりの資料で、クラウド版大規模モデルより読み取り精度が落ちる可能性がある
- 高密度な1ページ画像をまるごと入力すると、モデルの出力トークン上限に達し本文が途中で切れる可能性がある
- 見開きの中点クロップ（ノド検出なし）が、傾き・湾曲のあるスキャンでどの程度実用に耐えるか未検証
- Shortcutsの「モデルを使用」アクションが実際にPDF由来の画像添付でどう振る舞うか（1回の実行で複数画像をバッチ的に渡せるか、1画像ずつのループが必須か）は、Apple公式ヘルプの記述からは確定できておらず実機確認が必要

## 7. 次にやること（着手時）

1. 上記フローを実際にMacの「ショートカット」アプリで組む
2. 手元の縦書き史料（見開き含む）数ページで実行し、§6のリスクを検証
3. 精度が不十分な場合、①ページを上下分割してから読ませる、②プロンプトの読み順指示を調整、のいずれかで再検証
4. 実用に耐えると判断できたら、Shortcutsのリンクとして共有可能な形にまとめる
