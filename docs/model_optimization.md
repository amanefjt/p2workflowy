# Gemini Model Optimization Guide (V3: Golden Rewrite Edition)

p2workflowy V3 における、各 Gemini モデルの最適化設定、運用ノウハウ、および API レート制限に関する最新の知見まとめ。

## 1. 推奨モデルとルーティング戦略

V3（Golden Rewrite）では、用途に応じたモデルの**動的ルーティング**を確立している。

| 処理フェーズ (用途) | 推奨モデル | ポリシー |
| :--- | :--- | :--- |
| **Phase 1 (VLM / OCR)** | `gemini-3.1-flash-lite-preview` | **コスト・速度優先**。大量の画像処理を並行して行うためLiteで十分。 |
| **Phase 2 (DNA / Resume)** | `gemini-3-flash-preview` (高品質) | **品質主権**。論文全体の構造と意味を決定づける最重要フェーズのため、ティアや `--lite` 指定に関わらず「必ず高品質モデル」を使用。 |
| **Phase 4 (Translation)** | 動的選択 (Flash or Lite) | `--lite` 指定時や無料枠時は `3.1-flash-lite`。それ以外（通常時）は `3-flash-preview` を使用し、翻訳の重厚さを維持。 |

## 2. Thinking Level (思考レベル) の活用と罠

Gemini シリーズの `thinking_level: HIGH` は、学術論文のレジュメ生成や複雑な階層構造の翻訳において必須の機能である。

*   **絶大な効果**: JSON や XML タグ（RTT v3.4）を正確に維持し、代名詞や学術用語を文脈に合わせて推論する。
*   **「思考予算」の罠**: `Thinking: High` + 巨大コンテキスト（8万文字）の組み合わせは、API側で重いコンピュートタスクとして扱われる。これを複数同時に投げると深刻なストール（後述）を引き起こす。

## 3. 暴かれた「不都合な真実」：長大コンテキストと API キューイング

Phase 4 における翻訳速度を最大化する検証において、**「API 側のキューイングによるサイレント・ストール現象（TTFT 240秒問題）」** が発見された。

### 事象
*   8万文字近いコンテキスト（レジュメ等）を含むプロンプトを `ParallelTranslator` で **同時（並列）に 3つ以上** 投げた際、最初の1つは 10〜15秒で応答し始めるが、2つ目・3つ目は **最初の1文字が出るまで（TTFT）に 230〜255秒（約4分）も待たされる** 現象が発生。

### 原因の特定
過去（Trial A）ではこれを「JSON Schema（Structured Output）によるペナルティ」と誤認していたが、実際には **「巨大コンテキスト × 高並列」による LLM 側のコンピュート・スロットリング** であることが判明した。Google 側の API が GPU リソース保護のため、同一キーからの一斉送信リクエストを強制的に直列化（キュー待ち）していた。

### 解決策（Pacing と Context Chaining）
1.  **並列度の削減（直列化）**: 
    セクションごとに並列（`asyncio.gather` や Semaphore 3）で投げるのをやめ、**並列度 1〜2 に制限** する。これにより API 側でのキュー待ちが消滅し、タイムアウトの危険性がなくなる（総処理時間は変わらない）。
2.  **Context Chaining（文脈の数珠つなぎ）**:
    直列化の最大の恩恵として、**前のセクションの翻訳結果を、そのまま次のセクションの `previous_translation` コンテキストとして注入** できるようになった。これにより、章や節をまたいでも訳語の揺れがなくなり、一貫した最高品質の出力が可能となった。

## 4. API ティア管理とオートダウンシフト

- **有償版 (Paid)**: 
  - RPM 500 クォータ。セマフォは `15` 等の高い値が許容されるが、Phase 4 などの巨大コンテキストに対しては、あえて「直列（並列度1）」で送ることで安全かつ高品質に処理。
- **無償版 (Free)**: 
  - `429 RESOURCE_EXHAUSTED` を検知すると、一時的に Lite モデルへ切り替えてリトライ（ダウンシフト）。
