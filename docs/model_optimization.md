# p2workflowy Model Optimization Guide

p2workflowy V3 における Gemini モデルの**ルーティング戦略と実測ベンチマーク**。

> [!IMPORTANT]
> Gemini API 自体のモデル一覧・thinking_level 仕様・無料枠・廃止情報などの**共通知識は [`gemini_models.md`](gemini_models.md) を参照**。このファイルは p2workflowy 固有の運用情報のみを扱う。

## 1. フェーズ別モデルルーティング

V3（Golden Rewrite）では用途別に**動的ルーティング**を採用。モデル名の実態値は `core/coreprompts.json` の以下のキーが正本：

| キー | 現在値 |
|---|---|
| `DEFAULT_MODEL` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_FREE` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_FREE_POOL` | `["gemini-3.1-flash-lite", "gemini-3.5-flash-lite"]`（§7、`ModelRotator` が429/503時に使うローテーション先） |
| `DEFAULT_MODEL_VLM` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_RESUME` | `gemini-3.6-flash` |

ドキュメントとコードが乖離している場合はコード側を優先し、このドキュメントを修正すること。`@lru_cache` のため変更後はプロセス再起動が必須。

> [!NOTE]
> **ハイブリッド構成が既定（2026-07-11、Stage 2）**: レジュメ生成（論文全体・書籍全体・章単位）のみ `DEFAULT_MODEL_RESUME`（`gemini-3.6-flash`）を使い、翻訳を含むそれ以外の全フェーズは `DEFAULT_MODEL`（`gemini-3.1-flash-lite`）を使う。根拠は 2026-07-11 実施の Stage 1 モデル A/B（NST 論文）で Arm B（ハイブリッド）採用を決定したこと。GA 移行後の価格改定で Flash と Flash-Lite の価格差が約 6 倍に拡大したため、品質影響が大きいレジュメ生成のみ高モデルを残し、他は Lite に統一した。
> `DEFAULT_MODEL_RESUME` は TierManager のティア追従の対象外（`core/llm_client.py::get_default_model("resume")`）。無料ティアへダウンシフトした場合でもレジュメ生成は `DEFAULT_MODEL_RESUME` のまま実行され、これは無料枠のレート制限内に収まる想定。詳細は `docs/management/requirements_log.md`（2026-07-11 の Stage 1 A/B 記録）を参照。
>
> **2026-07-22: `DEFAULT_MODEL_RESUME` を `gemini-3.5-flash` → `gemini-3.6-flash` に切替**。`gemini_models.md` §4/§5 の実測により、両モデルは Rate Limit（無料枠・有料枠 Tier 2 とも）が完全一致、価格は `gemini-3.6-flash` の方が出力 -17% と純粋な改善（入力は同額）。公式後継でもあり、据え置くデメリットが見当たらないため切替えた。一方 `DEFAULT_MODEL` / `DEFAULT_MODEL_FREE` / `DEFAULT_MODEL_VLM`（`gemini-3.1-flash-lite`）は後継 `gemini-3.5-flash-lite` へは**切替えていない**：Rate Limit は一致するが価格が値上げ（入力+20%・出力+67%）で、コスト最優先というハイブリッド構成の設計意図と衝突するため。GA 化して間もない現時点では `gemini-3.1-flash-lite` の廃止予定もなく、現状維持のリスクは小さい。
>
> **「無料枠だから値上げは関係ない」わけではない点に注意**: Google の無料ティアは従量課金がそもそも $0 なので、無料キーで叩く限り §5 の価格改定は影響しない（効くのは Rate Limit のみで、これは新旧完全一致）。ただし `DEFAULT_MODEL`（PAID tier 既定）と `DEFAULT_MODEL_VLM`（`get_default_model("vlm")` は tier 分岐なしで常時参照、`core/llm_client.py:35-58`）は、管理者の `APP_ADMIN_PASSCODE` 経由やユーザー自身の有料キー、CLI の `GEMINI_API_KEY` フォールバック（§6）など**課金対象の有料キーで呼ばれた場合はそのまま実 billing に乗る**。さらに `DEFAULT_MODEL_FREE` も無料キー専用ではなく、有料キーのまま `TierManager` が 429/503 でモデルだけダウンシフトした場合にも使われうる（キー自体は据え置き）。したがって Lite 系の値上げは「無料キー由来のトラフィックには影響しないが、有料キーが絡む経路には影響する」というのが正確な理解であり、これが上記の現状維持判断の根拠になっている。
>
> **`gemini-3.5-flash`（旧 resume モデル）の単発リクエスト実効入力上限は `gemini_models.md` 記載の公称値（1,048,576 tok）よりかなり低い（2026-07-13 実測）**: 実測で約 186,000〜187,000 tok（文字数にして概ね 735,000 字前後）を超えると thinking の有無・`max_output_tokens` に関わらず一貫して `400 INVALID_ARGUMENT` になる（`gemini-3.1-flash-lite` は同じ入力で成功）。書籍モードの Phase 0 全文スキャン（`BookManager._generate_global_context`）はこの規模を容易に超えるため、`core/book_manager.py::RESUME_MODEL_SAFE_CHAR_LIMIT`（60万字）超で resume モデルを使わず `DEFAULT_MODEL` にフォールバックするガードを実装済み（章単位のレジュメは章テキスト規模が閾値未満のため対象外）。詳細は `troubleshooting_log.md` I-20。**この上限は `gemini-3.5-flash` での実測であり、切替後の `gemini-3.6-flash` では未検証**（ガード自体は保守的な値のためそのまま流用）。

### フェーズ別ルーティング表

| 処理フェーズ | 使用モデル | thinking | 設計意図 |
| :--- | :--- | :--- | :--- |
| **Phase 1 — PDF VLM / OCR** | `DEFAULT_MODEL_VLM` (Lite) | LOW | コスト・速度優先。大量の画像処理を並行するため Lite 固定 |
| **Phase 1 — テキスト構造解析** | `DEFAULT_MODEL_FREE` (Lite) | HIGH | 見出し抽出（TextStructureExtractor）。Lite でも精度十分 |
| **Phase 2 — レジュメ生成（論文/書籍全体/章）** | `DEFAULT_MODEL_RESUME` (Flash) | HIGH | ティア非追従。品質影響が大きいため無料モード下でも Flash を維持 |
| **Phase 2 — DNA / Keywords** | `DEFAULT_MODEL` (Lite) | HIGH | ハイブリッド構成によりレジュメ以外は Lite |
| **Phase 3 — 構造ツリー / TOC** | `DEFAULT_MODEL` (Lite) | HIGH | セクション境界の論理判断 |
| **Phase 4 — 翻訳** | `DEFAULT_MODEL`（Lite・通常）/ `DEFAULT_MODEL_FREE`（`--lite` / フォールバック時、同じく Lite） | HIGH | ハイブリッド構成により通常時も Lite。`--lite` 指定時や TierManager 発動時も同一モデル |

### thinking_level のフェーズ別設定

| フェーズ | thinking_level | 変更可否 |
| :--- | :--- | :--- |
| Phase 1 VLM / OCR | `LOW`（ハードコード） | 不可。画像→テキスト変換に思考は不要でコスト増になるだけ |
| Phase 1 テキスト構造解析 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |
| Phase 2 DNA・要約・キーワード | `HIGH`（デフォルト） | `--thinking LOW` で変更可。品質低下リスクあり |
| Phase 3 構造ツリー | `HIGH`（ハードコード） | 不可。セクション境界判断の精度に直結 |
| Phase 4 翻訳 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |

`--thinking LOW` フラグはコスト削減・速度優先の実験用途向け。本番処理では `HIGH` を維持することを推奨。

## 2. Phase 4 並列数の実測（2026-05-11）

AL 論文（18p / 9セクション / 17バッチ）で `concurrent = 1, 2, 4, 8` を各 2 回実行。

| concurrent | trial 1 | trial 2 | **平均** | avg TTFT | p90 TTFT | max TTFT |
|---|---|---|---|---|---|---|
| 1（直列） | 329s | 348s | **338.5s** | 14.5s | 20.6s | 22.5s |
| 2 | 221s | 302s | **261.4s** | 22.6s | 21.2s | 205.8s |
| **4（デフォルト）** | **119s** | **335s** | **226.8s** | 22.6s | 28.7s | 214.7s |
| 8 | 216s | 83s | **149.3s** | 21.6s | 24.3s | 212.7s |

### 判明した事実

- **「240s TTFT 問題」は定常現象ではなかった**。avg TTFT は 14〜31s であり、2026-04-04 の外れ値（障害 × Phase 1 分割バグの複合）に基づいた誤った前提だった。
- **直列化（concurrent=1）は有意に遅い**。2 回とも 329s・348s と安定して遅く、並列化の効果は確実に実証（concurrent=4 比で約 49% 遅い）。
- **concurrent=4 と 8 の優劣は各 2 回の計測では判断できない**。trial 間の振れ幅が 100s 以上ある。
- **分散の原因は API サーバー側の混雑**。concurrent を上げると「速いときはより速く、詰まるときはより詰まる」特性（concurrent=2/4/8 全てで max TTFT が 200s 超のスパイク）。

### 結論（2026-05-11時点）

**デフォルト `concurrent=4` を維持**。変更を正当化する統計的データがない限り 4 を採用する。「並列化によりスループットが向上する」が正しい説明（旧来の「240秒ストールを並列で相殺する」は不正確）。

> [!TIP]
> 直列化（`max_concurrent_sections = 1`）は約 50% スループット低下。

> [!NOTE]
> **2026-07-22改定: デフォルトを `concurrent=4` → `8` に変更**。§7 の無料枠Liteプール・ラウンドロビン実装後の実測（AL論文、`--lite`、単発計測）で `concurrent=8` が `concurrent=4` より明確に速いことを確認したため（Phase4所要時間 75s→64s、詳細は §7 参照）。ただし上表の2026-05-11時点のベンチマーク（ラウンドロビン導入前）では「trial間の振れ幅が100s以上あり4と8の優劣は判断できない」という結論だった点には注意 — 今回の変更は単発計測に基づく判断であり、複数trialでの統計的検証はまだ行っていない。

### AL論文（18ページ）1本あたりのコスト

> ★ Phase 4 のバッチ数はセクション数と 1 セクションあたりの文字量で変動。AL論文（9セクション）では 17バッチ（2026-05-11 実測）。

### ユーザー種別による動作

```
有料ユーザー（ハイブリッド構成、2026-07-11〜、resumeモデルは2026-07-22切替）:
  レジュメ生成（Phase 2、論文/書籍全体・章単位） → DEFAULT_MODEL_RESUME（gemini-3.6-flash、ティア非追従）
  それ以外の全フェーズ（翻訳を含む） → DEFAULT_MODEL（gemini-3.1-flash-lite）

無料ユーザー（TierManagerの自動制御）:
  レジュメ生成 → 常に DEFAULT_MODEL_RESUME（gemini-3.6-flash）のまま（ティア追従の対象外）
  それ以外のフェーズ → 初回から DEFAULT_MODEL（Lite）で処理
       ↓  429 RESOURCE_EXHAUSTED 発生時
  残り全体 → DEFAULT_MODEL_FREE (Lite、DEFAULT_MODEL と同一) へダウングレード（実質モデル変化なし）
```

実態として、DEFAULT_MODEL が Lite になったハイブリッド構成下では、**有料/無料ユーザー間の実行モデルの差はレジュメ生成（Phase 2）のみ**であり、翻訳を含むそれ以外のフェーズは有料・無料とも同じ Lite モデルで処理される。以前の「有料は全フェーズ Flash・無料は TierManager 発動で Lite に落ちる」という区別は現在の既定値には当てはまらない。

### 処理能力の目安（無料枠基準）

| ユーザー種別 | 実質動作モデル | ボトルネック | 1日 | 1ヶ月（30日） |
|---|---|---|---|---|
| **無料ユーザー** | Lite 固定（レジュメのみ Flash、ティア非追従） | Lite の RPD | **〜45〜68本** | **〜1,350〜2,040本** |
| **有料ユーザー** | Lite 固定（レジュメのみ Flash） | TPM / RPM | 実質無制限 | 実質無制限 |

> 無料ユーザーも有料ユーザーも翻訳等の大半のフェーズは Lite で処理される（ハイブリッド構成、§1 参照）。無料ユーザーは Lite の RPD（〜1,000〜1,500）÷ 実測22リクエスト（AL/NST論文実測、§5.4 の FREE候補設定 8チャンク/9,000字時点。Phase1: 1 + Phase2 DNA・キーワード: 2 + Phase4: 19、レジュメ生成は `DEFAULT_MODEL_RESUME`（`gemini-3.6-flash`）の別枠のため除外）≈ 45〜68本/日が上限（2026-07-20 実測に基づき更新。旧記載「136本/日・11リクエスト」は未検証の概算だった）。レジュメ生成のみ TierManager のティア追従の対象外で常に Flash 品質。
>
> **§7（2026-07-22実装）の`ModelRotator`により、この上限は理論上最大2倍程度まで拡張されうる**：`gemini-3.1-flash-lite`のRPDを使い切った時点で`gemini-3.5-flash-lite`（独立カウンター）へforward-onlyで切り替わるため。ただしラウンドロビンではなく429検知時のみの切替であり、実際にRPD枯渇を起こしてのライブ検証はまだ行っていない（上記45〜68本/日という実測値は`ModelRotator`導入前の単一モデル基準のまま、更新は未実施）。

#### 書籍モード（VLM）1冊あたりの概算とボトルネックの実感（2026-07-24、ユーザーとの対話で試算）

200ページ級の書籍1冊（VLMルート）を、AL論文（18ページ・FREE設定19バッチ）の実測値を章数分に外挿して概算すると：

| フェーズ | 概算根拠 | リクエスト数概算 |
|---|---|---|
| Phase 1 VLM OCR | 1ページ1リクエスト | 〜200回 |
| Phase 2（DNA+キーワード、章単位） | AL論文実測の2回 × 章数（レジュメ生成はFlash別枠のため除外） | 〜20〜25回 |
| Phase 3（構造ツリー） | 1〜2回 × 章数 | 〜10〜20回 |
| Phase 4（翻訳バッチ、FREE 8チャンク/9,000字） | AL論文実測19バッチ/18pを章あたりのページ数に比例配分 | 〜200〜250回 |
| **合計** | | **〜450〜500回** |

単一Liteモデルの無料RPD予算（〜1,000〜1,500）と比べると、**200ページ級1冊なら1日の枠内に収まる計算になる**（§7の`ModelRotator`が効けばさらに余裕）。RPDが実際に詰まってくるのは、1日に複数冊処理する場合や、500ページを超えるような大部の書籍1冊を単独で処理する場合。

> [!NOTE]
> あくまでAL論文（論文1本）の実測値を章数分に外挿しただけの推定であり、書籍モード×VLM×大規模文書での実測ではない（§7末尾の「未検証」項目と同じ限界）。実運用では、RPD予算の枯渇よりも **Google側の瞬間的な混雑（503 UNAVAILABLE）** や、**同一書籍セッションへの多重起動によるキャッシュ競合**（ロック機構がないため、`p2wbv`を前回のプロセスを止めずに再実行すると発生しうる）の方が体感の詰まりとして顕在化しやすい（2026-07-24 実例: `How to Read Ethnography.pdf` 処理中、Phase 2 初回リクエストで503発生、また同一書籍に対し`main.py --book`プロセスが4つ同時起動していたことが判明）。

### 処理速度（Phase 4 翻訳）

AL論文（10セクション / 19バッチ）、2026-05-11実測（`concurrent=4`、ラウンドロビン導入前）：

| 条件 | Phase 4 完走時間 |
|---|---|
| 有料 + Lite、concurrent=4（当時の既定） | 119s〜335s（平均 227s / 約4分。計測当時は Flash だが、モデル間の処理時間差は小さいため目安として有効） |
| 無料 + Lite | 同等（モデル間の処理時間差は小さい） |

Flash と Lite の処理時間差はほぼない。翻訳フェーズは有料・無料とも Lite で処理されるため、**品質差**は主にレジュメ生成の有無（ティア非追従の `DEFAULT_MODEL_RESUME`）による。

> [!NOTE]
> **2026-07-22実測（§7の無料枠ラウンドロビン導入後、`--lite`、AL論文、単発計測）**: concurrent=4・単一モデル（92s）→ concurrent=4・ラウンドロビン2モデル（75s、-18.5%）→ concurrent=8・ラウンドロビン2モデル（64s、対単一モデル比-30.4%）。詳細と「理論値2倍に届かない理由」の分析は §7 参照。

## 5. モデルのトークン仕様と Phase 4 プロンプト収支（2026-07-10 調査）

Phase 4 翻訳で実際に使うモデル（`DEFAULT_MODEL` = `gemini-3.1-flash-lite`、`--lite`/フォールバック時 `DEFAULT_MODEL_FREE` = 同じく `gemini-3.1-flash-lite`）の入出力トークン仕様と、現状の翻訳プロンプト 1 バッチあたりのトークン収支をまとめる。設計判断（ウィンドウ拡大やレジュメ注入の是非）はここでは行わず、事実と試算のみを記す。

> [!NOTE]
> 以下のコスト試算（§5.2〜§5.3）は 2026-07-10 調査時点、すなわち `DEFAULT_MODEL = gemini-3.5-flash` だったハイブリッド化前の数値。2026-07-11 のハイブリッド既定化（§1 参照）後は Phase 4 翻訳が `gemini-3.1-flash-lite`（Flash 比で入力 1/6・出力 1/6 の単価）で実行されるため、実際のコストは本節記載額より大幅に低い。数値の読み方は §1 のハイブリッド構成の注記と併せて解釈すること。

### 5.1 モデルのトークン上限と料金（2026-07-10 確認）

| モデル | 入力上限 | 出力上限 | 入力 $/1M | 出力 $/1M ★ | コンテキストキャッシュ $/1M |
|---|---|---|---|---|---|
| `gemini-3.5-flash` | 1,048,576 | 65,536 | $1.50 | $9.00 | $0.15 + 保管 $1.00/1M tok/時 |
| `gemini-3.1-flash-lite` | 1,048,576 | 65,536 | $0.25（text） | $1.50 | $0.025（text） + 保管 $1.00/1M tok/時 |

> ★ thinking トークンは出力トークンとして課金される（Phase 4 は `thinking_level=HIGH` がデフォルト）。

情報源（いずれも 2026-07-10 確認）:

- https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash （入出力上限）
- https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite （入出力上限）
- https://ai.google.dev/gemini-api/docs/pricing （料金・キャッシュ料金）

> [!NOTE]
> `gemini-3.5-flash` は 2026-05-19 の GA 化に伴い $0.50/$3.00 → **$1.50/$9.00** に改定された（`gemini-3-flash-preview` 比 3 倍、Lite 比 6 倍）。正本 `~/Code/shared/gemini_models.md` §5 は 2026-07-10 に更新・同期済み。

> [!NOTE]
> **実効入力上限（I-20）の実体はトークン数であり、`core/phase2_meta.py` の `MAX_INPUT_CHARS` 等の文字数閾値はあくまで不正確な代理指標（2026-07-21 追記）**: `troubleshooting_log.md` I-20 が実測した `gemini-3.5-flash` の単発リクエスト失敗境界は **734,997字(185,337tok)=OK ／ 738,015字(187,031tok)=FAIL** で、文字/トークン比は約 3.95〜3.97。一方 2026-07-21 に `Naven.pdf`（746,470字）を実運用で処理したところ **165,673tok で成功**しており、この文書の文字/トークン比は約 4.51 だった。文字数ベースでは I-20 の FAIL ラインを超えているが、トークン数では OK ラインに約 2 万 tok の余裕があった。つまり **英文の語彙密度・改行・空白・OCR 由来のノイズ次第で文字/トークン比は 3.9〜4.5 程度ブレる**ため、「N 字を超えたら必ず失敗する／超えなければ必ず成功する」という文字数だけの判断は不正確。加えて Google AI Developer Forum・`google-gemini/gemini-cli` の Issue には、Gemini 系モデル全般で公称の入力上限（1,048,576 tok）よりはるかに低い上限（例: 32,768 tok）で 400 が返る事例が複数報告されており、バックエンドの負荷・ルーティング・ティアによって実効上限自体が変動している可能性もある。したがって I-20 の「735,000字」および `MAX_INPUT_CHARS=1,500,000` は**特定日・特定文書での実測に基づく暫定的な安全ラインであり、恒久的な仕様値ではない**と理解すること。より頑健にするなら文字数ではなく `count_tokens` 相当でトークン数を実測してから閾値判定する方式への切替が望ましいが、現時点では未実装（2026-07-21 のレビューで指摘済み、対応は見送り）。

### 5.2 Phase 4 翻訳プロンプトの現状収支（1 バッチ）

> [!NOTE]
> 以下 §5.2・§5.3 の実測値・記述は **2026-07-10 時点（翻訳コンテキスト Stage 1 実装前）のスナップショット**であり、当時のプロンプト構成での測定を歴史的記録として残す。現況との差分は次のとおり：
> - **`resume_content`**: Stage 1（2026-07-11）で論文モードでも文献レジュメを毎バッチ注入するよう配線済み（下表・§5.3(b) の「なし／未注入」は Stage 1 前の状態）。
> - **`previous_translation`**: Stage 1 でスライディングウィンドウを「3 件 × 200 字の断片」から「連続 ~2,000 字（段落丸ごと）」へ変更済み（下表・§5.3(a) の「3 件 × 200 字」は Stage 1 前の状態）。
> - **`glossary`**: Stage 2（2026-07-12）で用語レイヤーに定義文が載るようになり、定義付きエントリは数十字程度増える（`docs/superpowers/specs/2026-07-11-translation-context-stage2-term-layer-design.md`）。

バッチ構成の決まり方（`core/engine/p4_translate/parallel_translator.py` + `core/llm_client.py::apply_tier_settings`）:

> [!NOTE]
> **2026-07-20 に flash-lite 前提で見直し済み**（詳細・根拠は §5.4）。下表は当時（3.5-flash 時代・
> 2026-04-03/04 導入）の値であり、現行値ではない。現行値: PAID 18チャンク/20,000字、FREE 8チャンク/9,000字。

| ティア | 最大チャンク数/バッチ（旧値） | 最大文字数/バッチ（旧値・英語原文） |
|---|---|---|
| PAID（デフォルト） | 10 | 11,000 |
| FREE | 5 | 6,000 |

プロンプトの構成要素と実測サイズ。実測値は `state/` に残る Phase 4 デバッグプロンプト 57 件（AL 論文ほか、論文モード・PAID ティア）の文字数分布に基づく:

| 構成要素 | 内容 | 実測（文字） | 理論上限（文字） |
|---|---|---|---|
| テンプレート固定部 | `TRANSLATION_PROMPT`（日本語、指示・訳例） | 約 1,350 | 同左 |
| `resume_content` | **論文モードでは常に「なし」**（書籍モードのみセクションレジュメを注入） | 2 | 書籍モード: 数千字規模 |
| `glossary` | DNA キーワード 11〜12 件（`data/glossary.csv` は現状不在） | 299〜535 | 用語数に比例 |
| `previous_translation` | スライディングウィンドウ: 直近 **3 件 × 200 字**（日本語） | ≤ 628 | 約 630 |
| `source_chunks` | 英語原文 + `<p2w_chunk_ID>` タグ | 中央値 2,744 / 最大 7,543 | 約 11,300（タグ込） |
| **合計** | | **中央値 4,829 / 最大 9,192** | **約 13,900** |

セクション境界でバッチが切れるため、実測では 11,000 字の上限に達するバッチはまれ（最大でも約 7,500 字）である点に注意。

**トークン換算**（粗い目安: 英語 ≒ 4 文字/トークン、日本語 ≒ 1〜1.5 文字/トークン。正確な値は `count_tokens` API でのみ確定する）:

| ケース | 英語部 | 日本語部 | 入力トークン概算 |
|---|---|---|---|
| 実測中央値バッチ | 約 2,700 字 → 約 700 tok | 約 2,100 字 → 1,400〜2,100 tok | **約 2,100〜2,800 tok** |
| 理論最大バッチ | 約 11,300 字 → 約 2,800 tok | 約 2,600 字 → 1,700〜2,600 tok | **約 4,500〜5,400 tok** |

**headroom**:

- **入力**: 理論最大バッチでも入力上限 1,048,576 tok の **約 0.5%**（約 200 倍の余裕）。入力側の制約は事実上存在しない。
- **出力**: 11,000 字の英文の日本語訳はおおむね 9,000〜13,000 字 ≒ 6,000〜13,000 tok。これに thinking トークン（HIGH）が加算される。パース側の安全弁（1 チャンク 3,000 字 × 10 = 最大 30,000 字 ≒ 2〜3 万 tok）を想定しても出力上限 65,536 tok の半分以下であり、余裕はあるが入力側ほど桁違いではない。
- **コスト構造**: 3.5-flash・最大バッチで入力 ≈ $0.008、出力（訳文 + thinking で 1 万 tok と仮定）≈ $0.09。**現行単価では出力（thinking 込み）がコストの支配項**であり、入力側の増減はコスト全体への影響が相対的に小さい。

### 5.3 拡大シナリオの試算

基準: AL 論文（9 セクション / 17 バッチ）、`gemini-3.5-flash`（$1.50/1M 入力）。日本語 1 字 ≒ 0.7〜1 tok の目安で換算。

#### (a) スライディングウィンドウの拡大（現状 3 件 × 200 字 → 例: 10 件 × 500 字）

- 注入量: 約 600 字 → 約 5,000 字（差分 +4,400 字 ≒ **+2,900〜4,400 tok/バッチ**）
- 論文 1 本（17 バッチ）: **+5〜7.5 万 tok** → 追加コスト **約 $0.07〜0.11/本**（Lite なら 1/6）
- 入力 headroom への影響: バッチ入力が約 5 千 → 約 1 万 tok になる程度で、上限の 1% 未満。無視できる。

#### (b) レジュメの毎バッチ注入（Phase 2 `resume_content`、実測 5,225〜5,903 字）

現状、Phase 2 が生成する文献全体レジュメは論文モードの翻訳プロンプトには**注入されていない**（`resume_content` は「なし」）。これを毎バッチ注入した場合:

- 注入量: 約 5,500 字 ≒ **+3,700〜5,500 tok/バッチ**
- 論文 1 本（17 バッチ）: **+6〜9.5 万 tok** → 追加コスト **約 $0.09〜0.14/本**（Lite なら 1/6）
- §3 の現状試算（1 本の総入力 ≈ 25 万 tok）に対して **+25〜38%** の入力増に相当

#### (c) (a)+(b) 同時適用

- バッチ入力は約 5 千 → 約 1.4 万 tok（約 2.8 倍）だが、入力上限の **1.4% 未満**でトークン上限上の支障はない。
- 追加コストは合算で **約 $0.16〜0.25/本**（3.5-flash）。出力側（訳文 + thinking）のコストは変わらないため、1 本あたり総コストへの影響は限定的。

> [!NOTE]
> レジュメ・glossary・テンプレート固定部は同一文献内の全バッチで不変のため、注入量を増やす場合はコンテキストキャッシュ（$0.15/1M、通常入力の 1/10）の適用余地がある。ただし最小キャッシュサイズ等の条件は別途要確認。ここでは事実の記載に留め、採否の判断は別スペックで行う。

## 5.4 バッチサイズ上限の flash-lite 前提での見直し（2026-07-20）

§5.2 のバッチ上限（PAID 10チャンク/11,000字、FREE 5チャンク/6,000字）は 2026-04-03/04 の初期実装時から
未変更で、選定根拠の記録もなかった。2026-07-11 のハイブリッド化以降 Phase 4 翻訳は PAID/FREE とも
`gemini-3.1-flash-lite` で動作するようになったため、flash-lite の実際の出力トークン仕様に基づいて上限を
再計算し、AL・NST 両論文で実測検証した。

### 上限の逆算

flash-lite の出力上限は 65,536 tok（Flash と同一、`gemini_models.md` L32）。thinking トークンも同じ
出力予算を消費する（§5.1 注記）。flash-lite 自体の thinking 消費量の実測データは存在しないため、
§5.2 の実測比率（11,000字入力 → 最大約13,000字 ≒ 13,000tok 出力、thinking除く）の悪いほうの端から
**約 1.18 tok/入力字** を導き、thinking＋バッファに出力予算の 60% を確保する保守的な前提を置いた：

```
テキスト用予算 = 65,536 × 40% ≈ 26,214 tok
入力文字数の理論上限 ≈ 26,214 ÷ 1.18 ≈ 22,200 字
```

これは「採用値」ではなく「これを超えると計算上危険」という天井。加えて、パーサーの
「1チャンク3,000字超で切り捨て」安全弁（`core/llm_client.py:461-466`、閉じタグ欠落による
チャンク混入対策）は `max_batch_chunks × 3,000字` が最悪ケースになるため、`max_batch_chunks` を
上げすぎると別経路でも出力上限に接近しうる点を考慮し、天井（約22,200字）より十分な余裕を残した
PAID **20,000字/18チャンク**、FREE **9,000字/8チャンク**を候補とした。

### 実測検証

AL論文（`Arbitrarysample.txt`）・NST論文（`NSTsample.txt`）で PAID候補・FREE候補をそれぞれ実行
（計4パターン・実バッチ数65件、実 API 呼び出し）。

| 論文 | ティア | バッチ数 | Phase4所要時間 | エラー/翻訳失敗/切り捨て警告/MAX_TOKENS |
|---|---|---|---|---|
| AL | PAID候補（20,000字/18ch） | 11 | 約53秒 | 0 |
| AL | FREE候補（9,000字/8ch） | 19 | 約91秒 | 0 |
| NST | PAID候補（20,000字/18ch） | 16（全16セクションが1バッチで収束） | 約54秒 | 0 |
| NST | FREE候補（9,000字/8ch） | 19 | 約93秒 | 0 |

### 判明した事実

- 65バッチ全てで「タグ正常抽出」。3,000字切り捨て警告・`MAX_TOKENS`・翻訳失敗はいずれも0件で、
  §5.4 冒頭の天井計算に対して実際にも余裕があることを確認した。
- PAID候補はバッチ数を大きく削減する（AL: 旧17バッチ相当 → 11バッチ、NST: 全16セクションが
  1バッチずつで収束）。セクション境界でバッチが切れる制約（§5.2）は変わらないため、削減幅は
  セクションあたりの文字量に依存する。
- 翻訳品質の詳細レビュー（`translation_review_checklist.md` によるサンプリング比較等）は今回
  実施していない。エラー有無の確認のみで採否判断する、というユーザー判断による。

### 結論

PAID/FREE のバッチ上限を **PAID: 18チャンク/20,000字、FREE: 8チャンク/9,000字** に変更（採用済み、
`core/llm_client.py::apply_tier_settings()` / `parallel_translator.py::ParallelTranslator` の
`DEFAULT_MAX_BATCH_CHUNKS`/`DEFAULT_MAX_BATCH_CHARS`）。FREE を PAID と完全同一にしなかったのは、
バッチ失敗時にチャンク単位の再試行がなく全チャンクが `【翻訳失敗】` になる現行のフォールバック
仕様（`parallel_translator.py`）を踏まえ、429/503 に遭遇しやすい FREE ティアでの1回の失敗の
被害を PAID より抑えるため（比率は変更前後でおよそ同水準を維持）。

> [!TIP]
> この変更はコスト削減より速度改善が主目的。§5.2 の分析どおり出力トークン（訳文＋thinking）が
> コストの支配項であり、バッチを大きくしても翻訳すべき総文字数は変わらないため総コストの削減効果は
> 限定的（バッチごとに重複するテンプレート固定部・glossary・previous_translation の重複回数減少分のみ）。
> 速度面は API 呼び出し回数減少によるラウンドトリップ・TTFT オーバーヘッドの削減で効く。

## 6. 複数APIキー運用: CLIのローテーション ＋ Webアプリの並行プール（2026-07-21）

§3/§4 の実測（無料枠で1日〜45〜68本処理可能）を踏まえ、CLI・Webアプリともに複数の無料枠APIキーを
使う運用に変更した。上位モデル（Opus）によるレビューで、素案では見落としていたプロセスグローバル
状態の競合バグ2件が発覚し、それを踏まえた設計になっている。

### 前提: 「無料/有料」はモデル指定ではなくキー（プロジェクト）の属性

`TierManager`（`core/llm_client.py`）が 429/503 検知時に行う「ダウンシフト」は、使用モデルを
Lite に切り替えるだけで、リクエスト先のAPIキー自体は変わらない。Gemini APIの無料/有料枠は
**APIキーが紐づくGoogle Cloudプロジェクトの課金設定**で決まり、さらに無料枠のRPM/RPD/TPMは
**キー単位ではなくプロジェクト単位**（同一プロジェクト内で複数キーを発行しても枠は増えない、
WebSearchで確認）。したがって複数キーで枠を実質的に増やすには、**それぞれ別のGCPプロジェクト**
でキーを発行する必要がある（同一Googleアカウント内で複数プロジェクトを作ればよく、別アカウントは
不要）。GCPのプロジェクト作成数にはアカウント単位のソフト上限があり、「無料枠を増やす目的での
複数プロジェクト作成」はGoogleの監視対象になりうるという指摘もコミュニティ報告にある（軽い
リスクとして記録するに留め、実装のブロッカーとはしない）。

### CLI: `GEMINI_API_KEY_FREE_1..4` → `GEMINI_API_KEY`（有料）の自動フォールバック

> [!NOTE]
> **2026-07-26 更新**: 無料キーの本数を 2 → **最大4本**（`GEMINI_API_KEY_FREE_1`〜`_4`）に拡張し、
> さらに「429/503 時にだけ前進する forward-only」に加えて、FREE tier では**キー × モデルの2軸
> ラウンドロビンで能動的に負荷分散**するようになった（§8）。未設定のキーは `configure()` が
> 自動的に除外するため、2本しか設定していない環境でも従来どおり動く。以下の記述は
> リアクティブなフォールバック側（今も有効）についてのもの。

`main.py` はデフォルトで無料キーを使い、429/503が続いた場合のみ最終手段として有料キーに
自動で切り替わる（テスト時・通常利用時ともに常に無料から使う）。`core/llm_client.py::KeyRotator`
（プロセスグローバルなシングルトン、forward-only）を新設し、`call_gemini`/`call_gemini_async`
のリトライループが429/503を検知した際、`tier_manager.downgrade()`（モデルのダウンシフト）に
加えてキー自体も次に進める。`main.py`が起動時に一度だけ`key_rotator.configure([...])`を呼ぶ。
`server.py`は一切呼ばないため、Webアプリの挙動には影響しない。

### Webアプリ: `GEMINI_API_KEY_WEB_1..5` を並行スロットとして使うプール

これまで`asyncio.Semaphore(1)`で全リクエストを完全直列化していたのを撤廃し、`server.py::WebKeyPool`
（無料キー最大5本）を同時実行スロットとして使う。あるキーが使用中の間は別のリクエストに別の
空きキーを割り当てる。空きが無ければ（6人目以降）待たせず即座に「混雑中」の失敗として
`task_status`に記録し、既存のステータスポーリングの仕組みでユーザーに表示する（フロントエンド
変更なし、`_pipeline_queue`によるキュー表示機構は完全撤去）。管理者パスコード・ユーザー自身の
APIキー入力の経路はこのプールを介さず今まで通り無制限に動く（5並行の枠にカウントされない）。

### 必須の副作用修正（Opusレビューで発覚、実装済み）

1. **`core/llm_client.py`のグローバルキャッシュ3点のスレッドローカル化**: Web側の各並行
   パイプラインは`asyncio.to_thread`でそれぞれ別スレッド・別イベントループで動くため、
   `_CLIENTS`（クライアントキャッシュ）・`_CACHED_LIMITERS`（レートリミッタキャッシュ）・
   `TierManager`の内部状態（`current_tier`/`was_downgraded`）はいずれも`threading.local()`
   ベースに変更した。外部から見えるAPI（`_get_client()`、`apply_tier_settings()`、
   `tier_manager.current_tier`等の属性アクセス）は無変更。これにより
   `reset_pipeline_state()`（`run_pipeline()`開始時に無条件実行）が呼び出したスレッド自身の
   状態しかクリアしなくなり、あるユーザーの処理開始が別の処理中ユーザーのキャッシュを消したり
   一時的に誤ったモデル階層に切り替えたりする競合が構造的に起こらなくなった。
   `apply_tier_settings(tier, api_key=...)`はさらに`(tier, api_key)`でレートリミッタを
   キーイングする（スレッドローカル化とは別軸、CLIのキーローテーションが複数キーを跨ぐ際に
   キーごとに正しい残余レートを持たせるため）。
2. **書籍モードの章ディレクトリを`state/book_sessions/`配下に移設**: `core/config.py::
   SessionState.MAX_STATE_SESSIONS=10`は`state/`直下の全セッション横断のグローバル上限で
   古い順に削除される。書籍モードは章ごとに`run_pipeline()`を呼び、従来は各章が`state/`
   直下の独立ディレクトリを使っていたため、1冊処理するだけでこの上限を回してしまっていた
   （[[book-mode-session-cache-global-cap]] 参照、既知の悩みとして報告済み）。Web側で5並行が
   走ると、あるユーザーの完了処理が別の処理中ユーザーのセッションディレクトリを削除して
   しまう実害のある競合になるため、章ディレクトリを`state/book_sessions/<book>_<fp>/
   chapters_state/ch<N>/`に物理的に移設した（`run_pipeline()`に`state_base_dir`パラメータを
   追加）。`book_sessions/`は元々グローバル上限の対象外かつ`MAX_BOOK_SESSIONS=5`で書籍単位の
   独自の上限管理下にあるため、章が個別セッションとして誤カウントされることもない。この修正は
   CLI・Web双方に効き、既知の悩みの解消にもなる。

### 既知の限界（今回は対応せず）

- 同一書籍の同時重複アップロード（`BookManager.session_dir`は内容フィンガープリント基準で
  `task_id`に基づかないため、異なる2ユーザーがほぼ同時に同一書籍をアップロードすると競合
  書き込みの可能性が残る）。
- ~~CLIのキーローテーションはプロセス内で永続・不可逆（1ファイル目で一時的な429に遭遇した
  だけでも、複数ファイル処理時に残り全ファイルが有料キーに固定される。`TierManager.
  downgrade()`と同じ設計思想）。~~ → **§9（2026-07-26）で解消**。レーン単位のクールダウン
  レジストリと`KeyRotator.best_available()`により、一時的な429で退避したキーもクールダウン
  が明ければ復帰できるようになった。詳細は §9 参照。
- ローテーションは429/503のみをトリガーにする。無効・失効した無料キーは`max_retries`回
  リトライして失敗し、有料キーへは切り替わらない。

## 7. 無料枠内での複数Liteモデル併用ローテーション（2026-07-22、実装済み）

§6が「別GCPプロジェクトでキーを複数発行してRPM/RPDを増やす」設計だったのに対し、こちらは
**同一プロジェクト・同一キー内でも複数のLiteモデルを使い分ければ枠を実質拡張できる**という
別軸の着想。AI Studioのレート制限ダッシュボードで、`gemini-3.1-flash-lite`と
`gemini-3.5-flash-lite`はRate Limit（RPM/RPD/TPMとも）が完全一致するが、**使用量は独立した
カウンター**であることを確認した（`gemini_models.md`§4の実測どおり上限が一致）。

> [!WARNING]
> **§9（2026-07-26）で「TPMは2モデルで共有」という前提を置いたが、同日の書籍モード章並列化
> 実走行検証で得た実データにより、この前提は誤りだったことが判明した**。実際の429の
> `quotaId` は `GenerateContentInputTokensPerModelPerMinute-FreeTier`（＝ **PerModel**、
> モデル単位で独立集計）であり、`quotaDimensions` にも対象モデルが明示されていた。
> 「上限の値が2モデルとも250,000で同一」という実測（`gemini_models.md`§4）を「集計
> カウンターも共有している」と誤って解釈していたのが原因。正しくは **RPM/RPD/TPM いずれも
> (プロジェクト×モデル) 単位で独立集計されており、TPM起因の429でもモデルローテーションは
> 有効な回復策になりうる**。訂正の詳細・実データ・コード修正は §9 末尾の追記を参照。

### 設計: `ModelRotator`（`core/llm_client.py`）

`KeyRotator`と対になる、forward-onlyのモデルローテーション機構。`TierManager`と同じく
スレッドローカル（Webの並行パイプラインにも対応するため）。対象は`core/coreprompts.json`の
`DEFAULT_MODEL_FREE_POOL`（`["gemini-3.1-flash-lite", "gemini-3.5-flash-lite"]`）。

- `call_gemini`/`call_gemini_async`のリトライループは、毎試行`current_model`を
  `model_rotator.resolve()`に通す。渡された`model`が呼び出し元でコンストラクタ時点に
  一度だけ解決された固定文字列（Phase1/2/3の主要呼び出し元の多数がこのパターン）でも、
  「今の解決済みモデルがプールのメンバーかどうか」だけで判定するため正しく効く。
- 429/503検知時、モデルローテーション（同一キー内で完結、client再生成不要）を
  §6のキーローテーションより**優先**して試みる。プールを使い切って初めて（`has_next()`が
  `False`になって初めて）キーローテーション・従来の待機付きダウンシフトにフォールバックする。
- `reset_pipeline_state()`で毎パイプライン開始時にプール先頭へ楽観的にリセットする
  （`tier_manager`のPAIDリセットと同じ思想）。書籍モードは章ごとに`run_pipeline()`を呼ぶため
  章ごとにリセットされるが、forward-onlyの`advance()`が各章内で429を機に即座に効くため
  容量拡張効果は損なわれない（無駄になるのは先頭モデルが枯渇していた場合の1回分の429往復のみ。
  拒否されたリクエスト自体はRPDを消費しない）。
- キーローテーション発生時（新しいキー＝別プロジェクトの独立枠）は`model_rotator.reset()`も
  呼び、新しいキー側でもプール先頭から使い始める。

### 許容したトレードオフ（ユーザー確認済み）

- **文書内でのモデル切替を許容**: forward-onlyのため、大きな書籍等でLite単体のRPDが尽きた
  場合、同一文書の処理途中で`gemini-3.1-flash-lite`→`gemini-3.5-flash-lite`に切り替わり、
  訳文のトーンがわずかに変わりうる。現状はLite単体でRPD枯渇＝そのまま失敗/停滞であり、
  切替は「本来失敗していたケースを完走させる」場合にのみ発生するため、既存挙動に対する
  正味の劣化ではなく改善と判断した。
- **`DEFAULT_MODEL_VLM`への波及も許容**: プール判定は`purpose`を意識しない純粋な文字列一致
  （`model_rotator.is_pool_member()`）のため、現状`DEFAULT_MODEL_VLM == DEFAULT_MODEL_FREE`
  （どちらも`gemini-3.1-flash-lite`）である間はPhase 1 VLM OCR呼び出しにも自然に波及する。
  両モデルともマルチモーダル対応のため実害なしと判断（将来`DEFAULT_MODEL_VLM`がプール外の
  値に変わればこの波及は自動的に消える）。
- thinking_levelのモデル間デフォルト差は実害なし: `_build_gemini_config()`は`model`に
  関わらず呼び出し側指定の`thinking_level`（省略時`HIGH`）を常に明示投入するため。

設計の全文（未決論点の検討過程・Opusレビュー結果を含む）は
`docs/superpowers/specs/2026-07-22-free-tier-multi-model-lite-pool-design.md`を参照。

### Phase4の速度改善: バッチ単位ラウンドロビン（2026-07-22、実装済み）

§7のここまでは「429検知時のみ切り替わるforward-only」設計で、RPD拡張（容量）が目的であり
速度には寄与しない。無料枠Liteプールの2モデルが**独立したRPM枠**を持つ性質を利用すれば、
429を待たずに最初からリクエストをバッチ単位で2モデルへ振り分けることで、Phase4翻訳の
スループット自体を上げられるのではという着想で追加実装した。

**実装**（`core/llm_client.py`・`core/engine/p4_translate/parallel_translator.py`）:

- `get_free_pool_rate_limiters(api_key)`: 無料枠Liteプールの各モデルに独立した
  `AsyncLimiter`（1 req/4s ≒ 15RPM相当）を割り当てて返す。既存の`apply_tier_settings()`の
  `(tier, api_key)`キーとは別に`(tier, api_key, model)`でキーイングするため、
  ローテーション用の共有リミッタとは衝突しない。
- `call_gemini`/`call_gemini_async`/`translate_batch`に`model_pinned: bool = False`を追加。
  `True`のとき、呼び出し元が明示した`model`を`ModelRotator.resolve()`/`advance()`で
  上書きしない。**これが無いと動作しない**: `resolve()`は「プールのメンバーならどれを渡しても
  現在のローテーション先へ差し替える」実装のため、ラウンドロビンで意図的に`pool[1]`を渡しても
  常に`pool[0]`（`current()`の初期値）へ引き戻されてしまい、ラウンドロビンが成立しなかった
  （実装中に発見）。プロアクティブな負荷分散（ラウンドロビン）とリアクティブなRPD枯渇対応
  （既存の`ModelRotator`）は役割が異なるため、`model_pinned`で明示的に分離した。
- `ParallelTranslator._pick_batch_target()`: FREE tierかつユーザーがモデル未指定の場合のみ、
  バッチ単位で`pool[rr_index % len(pool)]`とその専用リミッタを選ぶ（`model_pinned=True`）。
  ユーザーがモデルを明示指定した場合・PAID tierの場合は従来どおり単一`self.model`/
  `self.rate_limiter`のまま（挙動変更なし）。
- **トレードオフ**: `model_pinned=True`のバッチが429でRPD枯渇に遭遇した場合、
  `ModelRotator`のRPD拡張フォールバック（§7上部）は効かず、同一モデルへのダウンシフト+
  待機で再試行し、最終的に失敗すれば当該バッチは通常どおり「翻訳失敗」としてフォールバック
  する（`ParallelTranslator`の既存の失敗時ハンドリングに委ねる）。ラウンドロビン適用時は
  RPD枯渇時の自動延命効果を失うという既知の限界。

**速度測定**（AL論文、`--lite`、単発計測、Phase4のみの所要時間）:

| 設定 | Phase4所要時間 | 対単一モデル比 |
|---|---|---|
| 単一モデル、concurrent=4（導入前） | 92s | — |
| ラウンドロビン2モデル、concurrent=4 | 75s | -18.5% |
| ラウンドロビン2モデル、concurrent=8 | 64s | -30.4% |

**理論値（2倍）に届かない理由**:

1. **`max_concurrent_sections`（セマフォ）が実際のボトルネックだった**: concurrent=4のままでは
   同時に発行できるリクエスト数自体が4に制限されており、2つの独立したレートリミッタ
   （合計30RPM相当）を持っていても、それを飽和させるだけの同時実行数がなかった。
   concurrent=8に上げるとさらに短縮した（75s→64s）のはこれが裏付け。
2. **レートリミッタは「発行間隔の下限」に過ぎず、実際のボトルネックはAPIの応答レイテンシ
   （TTFT 6〜20秒程度）**: `AsyncLimiter(1, 4.0)`は「4秒に1回まで発行してよい」という制約
   であり、個々のリクエストの応答自体がそれより長くかかる場合、レートリミッタを2つに
   分割しても「応答待ちの間、他に投げられるリクエストがあるか」（＝同時実行数）に効果が
   左右される。
3. **ワークロードの端数・裾（tail）効果**: 10セクション・19バッチという小規模な処理では、
   実行終盤に残りセクション数が減り、両モデルを同時に稼働させ続けられる期間が短くなる
   （典型的な並列ジョブの立ち上がり・収束コスト）。より大規模な書籍等、バッチ数が多い処理
   ほど理論値に近づく可能性がある。

**`concurrent`のデフォルト変更**: 上記実測に基づき、`main.py --concurrent`・
`core/pipeline.py`・`core/phase4_translate.py`・`ParallelTranslator`の全デフォルトを
`4`→`8`に変更した（2026-05-11時点の旧ベンチマーク§2は「4と8の優劣は判断できない」との
結論だったが、ラウンドロビン導入後の状況が変わったための再判断。ただし今回も単発計測であり、
複数trialでの統計的検証はまだ行っていない点は同じ注意が必要）。

**未検証**: 大規模文書（書籍等、バッチ数が多い場合）での速度改善効果の実測、複数trialでの
統計的な安定性検証。

### VLM OCR（Phase1）への同様の適用（2026-07-22、実装済み）

Phase4の速度改善を踏まえ、「Phase1のVLM OCRも同じ手が使えるのでは」というユーザーからの
指摘で追加調査・実装した。調査の結果、VLMはPhase4と**構造的に異なる**ことが判明した:
`core/engine/p1_ingest/ocr_manager.py`の`OCRManager`は`VLM_SEMAPHORE_LIMIT=10`という
同時実行数の上限のみを持ち、Phase4の`AsyncLimiter`のような**クライアント側レートリミッタが
一切無い**（`apply_tier_settings()`を呼んでいない）。つまり「既存の1つのリミッタを2つに割る」
というPhase4の手法がそのまま使えず、実装としては「元々存在しなかったレートリミッタ＋
ラウンドロビンを新規追加する」形になった。

**ベースライン計測で実際に429を確認**: 変更前のコードでALpdf.pdf（18ページ）を
`--lite --pdf-mode full_vlm`で処理したところ、VLM OCR自体（Phase1、18ページを
Semaphore=10で並列発行）はエラー無く完走したが、**その直後のPhase2 DNA抽出リクエストが

自体は完走）。これはVLMの18リクエストだけで1分間のRPM枠をほぼ使い切っていたことの直接証拠。

**実装**（`core/engine/p1_ingest/ocr_manager.py`）: `OCRManager._pick_page_target()`を追加し、
Phase4の`_pick_batch_target()`と同じ設計思想でページ単位のラウンドロビンを行う。
`self.model`はコンストラクタで即座に解決せず（`None`のまま保持）、ページ処理のたびに
`_pick_page_target()`で動的決定する。`DEFAULT_MODEL_VLM`はtierに関わらず常に参照される値
（`get_default_model("vlm")`はtier追従しない）だが、ラウンドロビン自体はFREE tierかつ
モデル未指定の場合のみ適用する（PAID tierの有料キーは元々レート上限が十分高く、無料枠専用
ペース（1 req/4s/モデル）を適用するとむしろ有料ユーザーを不必要に遅くしてしまうため）。
Phase4で新設した`get_free_pool_rate_limiters()`をそのまま再利用している。

**速度測定**（AL PDF、18ページ、`--lite --pdf-mode full_vlm`、単発計測）:

| 設定 | Phase1(VLM OCR)所要時間 | 429/503 |
|---|---|---|
| 単一モデル（導入前） | 56s | Phase2で1回発生（自動復旧） |
| ラウンドロビン2モデル | **46s**（-18%） | **ゼロ** |

バーストするリクエスト」の性質が強く（`--concurrent`のような同時実行数の抑制も無いまま
全ページを一度にgatherする設計）、レート制限との衝突が起きやすい箇所だったことが、ラウンドロビン
導入前後の429有無の違いとしてはっきり表れた。

**未検証**: より大きな書籍・ページ数の多いPDFでの効果測定（今回の18ページでも明確な差が

## 8. 無料枠APIキー4本 × Liteモデル2種の2軸ラウンドロビン（2026-07-26、実装済み）

§6 が「無料キーを複数持つ」（ただし 429 時にだけ前進する forward-only ＝ 通常は1本目しか
使わない）、§7 が「同一キー内で複数の Lite モデルをバッチ/ページ単位でラウンドロビンする」
だったのを、**両者を掛け合わせて「キー軸 × モデル軸」の2軸ラウンドロビンに拡張**した。
ユーザーが `GEMINI_API_KEY_FREE_1`〜`_4` の4本を**すべて別GCPプロジェクト**で用意済みである
ことを確認したうえでの変更（無料枠は §6 のとおりプロジェクト単位なので、4本＝実質4倍の枠）。

### 設計

`(キー, モデル)` の組み合わせを**レーン**と呼ぶ。無料キー K 本 × Lite プール M モデルで
K×M レーンあり、各レーンは**別プロジェクト × 別モデルカウンター**なので独立した RPM 枠を持つ。
現状 4×2 = **8レーン ≒ 120RPM 相当**（Lite 無料枠は 15RPM/プロジェクト/モデル）。

- `KeyRotator.pool_keys()`: tier が `"free"` のキーだけを返す。有料キーを含めないのは、
  無料枠専用ペース（1 req/4s/レーン）のリミッタを有料キーに被せると有料ユーザーを不必要に
  遅くしてしまうため（§7 で PAID tier をラウンドロビン対象外にしたのと同じ理由）。
- `ParallelTranslator._pick_batch_target()` / `OCRManager._pick_page_target()` はいずれも
  `(api_key, model, rate_limiter, model_pinned, key_pinned)` を返すように拡張。通し番号 `i` に
  対して **`key = keys[i % K]`, `model = models[(i // K) % M]`**。こうすると連続するリクエストが
  必ず別キーへ散り（同一プロジェクトの枠を連打しない）、K×M 回でちょうど全レーンを一巡する。
- リミッタは §7 の `get_free_pool_rate_limiters(api_key)` をそのまま流用する。既に
  `(tier, api_key, model)` でキーイングされているため、**割り当て先のキーを渡すだけで**
  レーンごとに独立した `AsyncLimiter` が得られる（新規の仕組みは不要だった）。
- `call_gemini` / `call_gemini_async` / `translate_batch` に **`key_pinned: bool = False`** を追加。
  `True` のとき `effective_key = key_rotator.current()` の上書きを行わず、呼び出し元が渡した
  `api_key` をそのまま使う。**§7 で `model_pinned` を追加したのと完全に同じ理由**で、これが
  無いとラウンドロビンで意図的に free_2 を渡しても常に `current()` ＝ free_1 に引き戻されて
  分散が成立しない。実装も `model_pinned` の鏡写し（429 時のキーローテーション条件に
  `not key_pinned` を追加しただけ）。
- **適用条件は §7 と完全に同一**: FREE tier かつユーザーがモデル未指定のときだけ。PAID tier・
  ユーザー明示指定時は従来の単一キー/単一リミッタのまま（挙動一切変更なし）。無料キーが
  1本以下の環境（`len(pool_keys()) <= 1`）ではキー軸が自然に無効化され、§7 のモデル軸だけの
  ラウンドロビンにそのままフォールバックする。

### 章並列化のためのフック: `KeyRotator.restrict_to()`（今回は誰も呼ばない）

書籍モードを「章ごとに別スレッドで `run_pipeline()`」へ並列化する後続タスクの下ごしらえ。
レートリミッタは §6 のとおり `threading.local()` ベースなので、複数スレッドが同じレーンを
共有すると同じ枠を多重に叩いて 429 が多発する。そこで「章スレッドごとにキーを1本ずつ排他的に
割り当てる」ために、`restrict_to(keys, tiers=None)` / `clear_restriction()` を追加した。

- 制限を設定したスレッドだけ `current()` / `pool_keys()` / `advance()` / `has_next()` /
  `current_tier()` / `index` / `count` がその部分集合に対して動く。
- **制限を設定していないスレッドの挙動はプロセスグローバルな `_keys`/`_index` そのままで
  完全に不変**（ここを壊すと CLI 論文モードが全滅するため、スレッドローカル側は
  グローバル状態に一切書き込まない実装にしてある）。
- 今回のタスクでは誰も呼ばない。ユニットテスト（別スレッドから見て影響がないこと・
  制限中の `advance()` がグローバル index を動かさないこと）のみで担保している。

### 許容したトレードオフ

- **`key_pinned=True` のリクエストは 429 時の延命が効かない**: §7 の `model_pinned` と完全に
  同じ扱い。ラウンドロビンで割り当てられたリクエストが 429 に遭遇しても `KeyRotator.advance()`
  による有料キーへのフォールバックは発火せず、同一レーンでのダウンシフト+待機で再試行し、
  最終的に失敗すれば既存の失敗ハンドリング（Phase4 なら `【翻訳失敗】`、Phase1 なら
  `pdf_ingester` のフォールバック）に委ねる。**そう判断した根拠**: プロアクティブな負荷分散と
  リアクティブなフォールバックを混ぜると、(a) どのレーンが本当に枯渇しているのかを
  カウンタが追えなくなり、(b) 1本のバッチの一時的な 429 でプロセス全体が有料キーに移って
  しまう（§6 の既知の限界「forward-only は不可逆」がラウンドロビン下では確率的に必ず
  起きる）。そもそも 8レーン ≒ 120RPM を能動的に使い切る設計では、単一レーンの 429 は
  「枠切れ」ではなく「一時的な混雑」である可能性のほうが高い。
- **無料キー4本の運用リスク**は §6 の記載のまま（無料枠拡張目的の複数プロジェクト作成は
  Google の監視対象になりうるというコミュニティ報告）。今回もブロッカーとはしない。

## 9. レーン単位のクールダウン（circuit breaker）と KeyRotator の可逆化（2026-07-26、実装済み）

§6 の「既知の限界」に記録していた「CLIのキーローテーションはプロセス内で永続・不可逆（1
ファイル目の一時的な429で残り全ファイルが有料キーに固定される）」を解消するための実装。
§8 実装直後の続きタスクとして着手した。

### 設計

**問題**: `KeyRotator`/`ModelRotator` はいずれも forward-only（`TierManager.downgrade()` と
同じ設計思想）。これは「一時的な RPM/TPM 超過（1分待てば回復する）」と「恒久的な RPD 枯渇
（その日は回復しない）」を区別せず、どちらも「二度と戻らない」扱いにしていた。無料キーが
4本になった§8以降、この不可逆性は「一瞬の429で無料枠3本ぶんを捨てて有料キーへ落ちる」という
実害になる。

**解決策**: `(api_key, model)` 単位の**レーン**ごとに「いつまで使用不可か」を記録する
`LaneCooldownRegistry`（`core/llm_client.py::lane_cooldown`）を新設し、429/503を検知したら
そのレーンをクールダウンに入れる。ラウンドロビン（`pick_lane()`）はクールダウン中のレーンを
避けて生きているレーンを選び、`KeyRotator.best_available()` は 429 起点のフォールバックで
forward-only ではなく「クールダウン中でないキーのうち最も優先度の高いもの」を選ぶ。
クールダウンが明ければ、そのレーン・そのキーは自然に候補へ戻る（＝可逆化）。

#### `LaneCooldownRegistry`: プロセスグローバル + Lock（意図的にスレッドローカルにしない）

`TierManager`/`ModelRotator` は Web の並行パイプライン対応のため `threading.local()` ベース
だが、`lane_cooldown` は**逆に意図的にプロセスグローバル**（`dict` + `threading.Lock`）にした。
「このキーのこのモデルは枯渇している」という事実はスレッドを跨いで共有されるのが正しく、
`(api_key, model)` でキーイングするため Web の別ユーザー（＝別キー）を誤って巻き込むことも
ない。次に控えている書籍の章並列化（章スレッドごとに `KeyRotator.restrict_to()` で別キーを
排他割り当て、§8）でも、あるキーが枯渇している事実は全章スレッドから見えるべきなので、この
設計は章並列化とも自然に整合する。

#### クールダウン秒数の決め方

429のエラーボディに含まれる `RetryInfo.retryDelay` と `quotaMetric`/`quotaId` を使う
（下記「実際に取得できたか」参照）。

- **quotaMetric/quotaId による分類**（`_classify_quota_violation()`）: 文字列に `"token"` を
  含めば TPM、`"day"` を含めば RPD、`"minute"`/`"requests"` を含めば RPM、それ以外は
  `unknown`（503含む）。
- **RPM/TPM起因**: 1分単位のスライディングウィンドウでリセットされるため既定 **60秒**。
  `retryDelay` が取れれば **1〜120秒**にクランプして使う（120秒＝60秒の2倍の安全マージン。
  `retryDelay`は不正確という報告があるため、回復スケールを大きく超える値は信用しない）。
- **RPD起因**: その日いっぱい回復しない（太平洋時間の深夜にリセット）。`retryDelay`は
  短すぎることが多く信用できないため採用せず、**次の太平洋時間深夜までの残り秒数を実計算**
  して使う（下限1時間・上限24時間でクランプ。計算誤り・タイムゾーンデータ異常時の安全弁）。
- **quotaMetric不明（503含む）**: 安全側で既定 **30秒**。RPM/TPMより短くしているのは、
  429/503全般では「本当にリソース枯渇かどうか」自体が不確かなケース（一時的なサーバ混雑等）
  を含むため、長時間ふさぐより早めに再挑戦させる方が実害が小さいという判断。

#### 全レーンがクールダウン中の場合のフォールバック

`pick_lane()` は K×M回探索して生きているレーンが見つからなければ `None` を返す。呼び出し元
（`ParallelTranslator._pick_batch_target()` / `OCRManager._pick_page_target()`）は `None` の
場合、クールダウンを無視した §8 従来どおりの割り当てにフォールバックする（例外を投げない・
処理を止めない）。同様に `KeyRotator.best_available()` も、使用可能なキーが1つも無ければ
既存の forward-only `advance()` にフォールバックする。「新しい情報が無い以上、従来どおりの
挙動に委ねるのが安全」という判断で、§6/§7/§8 とも共通する設計思想。

#### TPM起因の429のモデルローテーション扱い（2026-07-26 実データにより訂正）

**当初の実装（本節、初版）**: 事前調査（`~/.claude/jobs/b0473b65/tmp/research_gemma_multikey.md`
項目B）が「無料枠Liteプールの2モデルはTPM枠を共有している」（`gemini_models.md`§4実測で両モデル
とも上限値が250,000で同一）と推定していたことを根拠に、TPM起因の429では
`ModelRotator.advance()` を試さずキー切替（`KeyRotator.best_available()`）へ直行する実装に
していた。

> [!WARNING]
> **この前提は誤りだったことが、書籍モード章並列化の実走行検証（同日 2026-07-26、
> `relationspdf.pdf` の直列ベースライン実行、10:27:34）で判明した。** 実際に踏んだ429の
> レスポンスJSONは以下のとおりで、`quotaId` が明確に **`...PerModelPerMinute-FreeTier`**
> （＝モデル単位で独立集計）であり、`quotaDimensions` にも対象モデル
> （`gemini-3.1-flash-lite`）が明示されていた。
> ```
> quotaMetric: generativelanguage.googleapis.com/generate_content_free_tier_input_token_count
> quotaId:     GenerateContentInputTokensPerModelPerMinute-FreeTier
> quotaDimensions: {'location': 'global', 'model': 'gemini-3.1-flash-lite'}
> quotaValue:  250000
> RetryInfo:   retryDelay: '25s'
> ```
> 事前調査レポート自身、実は同じ節の少し手前で「`gemini-3.1-flash-lite` と
> `gemini-3.5-flash-lite` は上限が一致するが使用量カウンターは独立」と正しく実測していた
> （§7参照）。にもかかわらず後段で「TPMは2モデルで共有」という矛盾した結論を導いていたのは、
> **「上限の値が同じ」と「集計カウンターを共有している」を混同した誤り**だったと考えられる。
> `quotaId` の命名（`PerModelPerMinute`）どおり、TPM（入力トークン毎分）もモデル単位で
> 独立集計されているなら、TPM起因の429でもモデルローテーション（同一プロジェクト内で完結し、
> キー切替よりコストが低い）は有効な回復策のはずである。

**訂正後の実装**: `quotaId`（または詳細情報全体）に **`PerModel`** という文字列が確認できる
場合に限り、TPM起因の429でもモデルローテーションを試す（`_is_model_scoped_quota()`）。
確認できない場合（quotaIdの形式が不明、503でdetailsが乏しい等）は、根拠のない前提を置かず、
保守的に従来どおりモデルローテーションをスキップしてキー切替へ直行する。TPM以外
（RPM/RPD/unknown）の扱いは変更していない。

```python
tpm_blocks_model_rotation = quota_kind == "tpm" and not _is_model_scoped_quota(e)
if (is_resource_limit and not model_pinned and not tpm_blocks_model_rotation
        and model_rotator.is_pool_member(current_model) and model_rotator.has_next()):
    ...  # モデルローテーションを試す
```

**実データに基づく検証**: `tests/unit/test_llm_client.py` に、上記の実際の429レスポンス
JSONをそのまま使ったテストを追加（`REAL_TPM_429_DETAILS`）。`_classify_quota_violation()` が
`"tpm"`、`_extract_retry_delay_seconds()` が `25.0`、新設した `_is_model_scoped_quota()` が
`True` を返すことを確認。また、実際の `quotaId` 文字列を使った統合テストで、この429の直後に
モデルローテーション（キー切替ではなく）が発火することも確認した。既存の
「TPM起因ならモデルローテーションをスキップ」テストは、`PerModel` の手がかりが無い合成
quotaId（`GenerateContentInputTokensPerMinute-FreeTier`、実データではなく判別不能ケースを
模したもの）を使うよう書き換え、そちらは従来どおりキー切替に直行することを確認した。

**この訂正が§8の章並列化と整合する理由**: 章並列化で章スレッドごとにキーを1本ずつ排他
割り当てする設計（`KeyRotator.restrict_to()`）は、無料キーという有限資源の消費を最小化する
狙いも含む。TPM起因の429で無条件にキー切替（＝別の章スレッドが使っているかもしれない
プールの残りキーを消費）していた旧実装より、まず同一キー内のモデル切替で回復を試みる
訂正後の実装のほうが、章並列化時のキープール消費を抑えられる点でも整合的。

**未検証**: 実際にモデルローテーションで回復するケース（TPM超過が本当にモデル単位でのみ
発生し、切替後即座に成功する）は、書籍実走行では発生しなかった（今回踏んだTPM429は直列
ベースラインの1件のみで、旧実装のままキー切替で回復した。訂正後の実装でこの429を再現して
モデルローテーションが実際に成功することの実地確認はできていない）。RPM/RPDのquotaId命名が
同様に`PerModel`を含むかどうかも未確認（今回の実走行では発生しなかった）。

#### `KeyRotator.best_available()`: `advance()` はそのまま、新規メソッドで使い分け

既存の `advance()`（forward-only、既存テストが依存）はシグネチャ・挙動とも一切変更していない。
`best_available(is_available)` を新規追加し、リトライループはこちらを使う。優先順位は
`configure()` に渡した並び順（CLI/Web とも free キーを先・paid キーを最後に渡す運用）を
そのまま使うため、「無料キーが1本でも生きているなら有料キーには落ちない」という既存の優先

## 10. 書籍モードの章並列化（2026-07-26、実装済み）

§8 で用意した `KeyRotator.restrict_to()`/`clear_restriction()` のフック（当時は「誰も呼ばない」
下ごしらえだった）を実際に使い、書籍モードの章ループ（`core/book_manager.py::BookManager.run()`）
を `ThreadPoolExecutor` で並列化した。§8 の実測で判明した「論文1本では `max_concurrent_sections`
がセクション数の少なさ（AL論文9セクション）で頭打ちになる」という制約に対し、**章を並列に走らせて
同時実行数そのものを増やす**のが8レーンの投資を活かす取り分だった。

### なぜ Web 版では無効なのか

`server.py` は `key_rotator.configure()` を一切呼ばない（1リクエスト＝1キー、`WebKeyPool` による
同時実行スロット制御、§6）。レートリミッタ・`TierManager`・`ModelRotator` はいずれも
`threading.local()` ベース（§6〜§8）なので、もし Web 側で章並列を有効にすると、Web の並行処理
（`asyncio.to_thread` による別スレッド）と書籍の章並列（別スレッド）が二重に絡み合い、複数の
章スレッドが同一キーの同一レーンを共有して「自分は15RPM使える」と多重に思い込み、429が多発する。
これを避けるため、**有効化条件を `key_rotator.is_configured() and len(pool_keys()) >= 2` の
一点に絞った**（`BookManager.run()` 内で判定）。`server.py` は `configure()` を呼ばないため
`is_configured()` が常に `False` で、章並列は構造的に発火しない＝Web版の挙動は不変。CLI 側でも
無料キーが1本以下の環境（`GEMINI_API_KEY_FREE_1` のみ設定等）では同じ理由で常に完全直列に
フォールバックする。

### なぜ章スレッドごとにキーを排他割り当てするのか

`ParallelTranslator._pick_batch_target()` / `OCRManager._pick_page_target()` の §8 ラウンドロビンは
「1つのパイプライン実行内で複数リクエストをキー×モデルへ能動的に分散する」設計であり、**単一
スレッド内で `key_rotator.pool_keys()` を読んで割り当てる**ことを前提にしている。章並列化で
複数スレッドが同時に同じ `pool_keys()`（全4本）を見てラウンドロビンすると、スレッドごとの
レートリミッタ（threading.local）は互いを認識できないため、同じ (キー, モデル) レーンへ複数
スレッドから同時に発行してしまい、実質的な RPM が予算超過する。これを避けるため、各章スレッドは
`run_one_chapter()` 開始前に `key_rotator.restrict_to([自分に割り当てられたキー], ["free"])` を
呼び、**そのスレッドから見える `pool_keys()`/`current()` を1本に縮退させる**。章スレッド内部では
引き続き `ParallelTranslator`/`OCRManager` の §7 モデル軸ラウンドロビン（2 Lite モデル）は効く
（`pool_keys()` が1本を返すので `key = keys[i % 1]` は常に同じ1本、`model` だけが2モデル間で
回る）。キー本数 K が章数 N より少ない場合に備え、キーを `queue.Queue` にプールし、章タスクが
1本取り出して終わったら返す方式にした。これにより「同時に同じキーを使う章は高々1つ」が
（ラウンドロビンのような計算式ではなく）**キューの排他取得によって構造的に保証**される。

### 実装

- `BookManager.run()` に `book_concurrency: Optional[int] = None` / `vlm_concurrency: Optional[int] = None`
  引数を追加。`main.py` に `--book-concurrency` フラグを追加して配線（`--vlm-concurrency` は
  今回は追加していない、後述）。
- 章単位 resume のスキップ判定（`output_paths.json` 確認）は LLM を呼ばない安価な処理のため、
  並列投入前に直列で済ませる（スキップされた章はスレッドを消費しない）。
- 有効化条件を満たさない場合・`len(pending) <= 1`（並列化する意味がある章が1つ以下）の場合は
  従来どおりの直列ループにフォールバックする。`book_concurrency=1` は有効化条件を満たしても
  常に直列にする（回帰時の逃げ道）。
- 有効化条件を満たす場合、既定の並列度は **無料キー本数と処理対象章数（スキップ後）の小さい方**。
  `book_concurrency` 明示指定時はそれを使う（`ThreadPoolExecutor(max_workers=...)`。ワーカー数が

  `set_log_prefix(None)` を対にする。個々の `print_log()` 呼び出し箇所（`core/` 全体に散在）を

  APIレート負荷の両方が章並列数倍に積み上がるため、単一章前提の20という値をそのまま章数分
  掛けるのは危険と判断。下限4は1章あたりの並列性を極端に潰さないための保守的な床で、実測に

  `BookManager.run()` に露出しており、明示指定すれば自動計算を上書きできるが、利用者が
  個別に調整したい場面が具体化していないため今回はCLI配線を見送った）。

### 書籍モードの実走行検証（2026-07-26、3章限定、`relationspdf.pdf`）

ユーザー判断により、`data/input/Booksample/relations/relationspdf.pdf`（Booksample中最小、282頁）

実走行した（1冊丸ごとではなく3章限定）。Phase 0（グローバルコンテキスト生成・章分割）は
両条件で共通のキャッシュ（`global_context.json`・`chapters/`）を使い回し、条件間で公平に
比較できるようにした。章単位resumeのスキップ機構が効かないよう、条件を切り替える前に必ず
`state/book_sessions/relationspdf_.../chapters_state/` のみを削除した（`global_context.json`・
`chapters/` は保持）。

**完走・統合順序**（両条件とも）: 3章とも成功、失敗章0件。統合後の `relationspdf_p2.txt` の
章出現順は直列・並列とも `Preface → Introductions: The Compulsion of Relations →
1. Experimentations, English and Otherwise`（book本来の並び順）で完全一致。並列条件では
実際の完了順は `Preface(ch1) → Introductions(ch2) → Experimentations(ch3)` または
`ch1 → ch2 → ch3` 以外の順（実行によりばらつく、章ごとのAPIレイテンシ次第）だったが、
`chapter_sessions[idx]` へのインデックス書き込み方式により出力順は完了順に引きずられず
本来の並び順を維持することを実地で確認した。

**429/503件数**（直列1回・並列2回、計3回実行。並列は1回目で429/503の質的差異確認のため
ログ計装無しの初回実行、2回目は章ごとの使用キーをログに明示するため計装を追加した再実行。
以下「並列(1)」「並列(2)」と区別する）:

| 条件 | 429件数 | 503件数 | 【翻訳失敗】 | 総所要時間 |
|---|---|---|---|---|
| 直列（`--book-concurrency 1`） | **1件**（TPM起因、Phase0グロッサリー生成時） | 0件 | 0件 | 820秒（13分40秒） |
| 並列(1)（計装前、既定=3並列） | 0件 | **2件**（503 UNAVAILABLE、ch1・ch2） | 0件 | 448秒（7分28秒） |
| 並列(2)（計装後、既定=3並列） | 0件 | 0件 | 0件（空レスポンス1件はリトライで自己回復） | 642秒（10分42秒） |

**429/503の質的な区別が重要**: 並列(1)の2件はいずれも `503 UNAVAILABLE`
（`This model is currently experiencing high demand`）で、モデル側の一時的な高負荷が原因の
サーバ起因エラーであり、**クォータ超過（429 RESOURCE_EXHAUSTED）ではない**。両方とも
`quotaMetric` 等の手がかりが無い（`unknown`分類）ため`_lane_cooldown_seconds()`は30秒の
既定クールダウンを適用し、実際にはモデルローテーション（`gemini-3.5-flash-lite`へ切替）で
数秒後に自己回復した。**章並列化がクォータ起因の429を増やした証拠は無い**（直列でも429が
1件発生しており、むしろ並列2回とも429は0件）。ただし試行回数が少なく（各条件1〜2回）
統計的な結論は出せない。

**所要時間の解釈**: 並列(1)は直列比で**約1.83倍**（820s→448s）の速度改善。一方、同一条件の
並列(2)は642秒で直列比**約1.28倍**にとどまった。この差は主にAPI側のテールレイテンシの
ばらつきによるもの（並列(2)ではch3の翻訳中に単発リクエストが60.3秒かかるスパイクと、
空レスポンスによる再試行が発生し、章の完了が押した）。§2/§8で既知の「API側の混雑で
trial間に100秒単位の振れ幅が出る」現象と整合的であり、単発計測2回では速度改善の正確な倍率は
断定できない。それでも**両条件とも直列より明確に速い**ことは確認できた。

**キー割り当ての分散確認**（並列(2)、計装ログより）: 各章スレッドが実際に別々の無料キーへ

### 未検証・既知の限界

- **1冊丸ごとの実走行は未実施**（ユーザー判断により3章限定に留めた）。500ページ級の大部な
  書籍や、章数がキー本数（4本）を超えるケースでのキュープール運用は今回の3章では検証できて
  いない。
- **VLM同時実行数の按分式（`max(4, 20 // effective_concurrency)`）は実測に基づく値ではなく、
  「単一章前提の20を並列数で割る」という保守的な仮説に基づく初期値**。今回の3章はいずれも
  Doclingルート（VLM不使用）だったため、VLM同時実行数の按分式自体は実走行で検証できていない。
- **`max_concurrent_sections`（Phase4セクション同時実行数）は章並列化に伴って調整していない**。
  1章あたり8のまま据え置き。章並列4×Phase4セクション並列8＝理論上最大32同時リクエストに
  なりうるが、§8の8レーン設計（無料キー4×モデル2）は章あたり1キー×モデル2＝2レーンに縮退する
  ため、実際にリミッタを通る同時発行数は章あたり2レーン相当のペースに絞られる。理論上の
  「32同時」という数字がそのままAPIへのバースト幅になるわけではないと考えているが、今回の
  3章並列（3並列×Phase4セクション並列8）でも429/503いずれかの増加は観測されなかった
  （ただし試行回数が少ないため確定的とは言えない）。
- **無料キー4本のうち3本以上が同時に枯渇している状況（キューが長時間空になる）でのデッドロック
  的な挙動は未検証**。設計上は `key_queue.get()` がブロックするだけで、他の章スレッドがキーを
  返却すれば再開されるため理論上は問題ないはずだが、実測での確認はしていない（今回は無料キー
  4本に対し3並列のみで、全キー枯渇の状況は発生しなかった）。
- **書籍モードのメモリ使用量の実測はしていない**（4章×ページ並列で数十ページ分の画像が同時に
  載りうるという懸念に対し、VLM同時実行数を絞る対策のみ実装。今回の3章はDoclingルートで
  VLM画像を使わなかったため、この懸念自体を実地検証できていない）。
- **速度改善の倍率は単発計測2回のみ**（1.83倍・1.28倍とばらつきが大きい）。§2/§8と同じ注意
  だが、章数が3と少ないぶんテールレイテンシの影響を相対的に受けやすく、より大きな章数での
  複数trial検証が望ましい。
- **TPM訂正後の実装で、実際にモデルローテーションが429を回復させるケースは未実測**（今回
  踏んだTPM429は訂正前の実装で発生し、キー切替で回復した。訂正後のコードでこの429を再現して
  モデルローテーションが実際に成功することの実地確認はできていない）。
