# トラブルシューティングログ (Troubleshooting Log)

## 2026-03-17: 目次（TOC）の一部エントリーの欠落

**事象**:
- [Phase 3] `psdpdf.pdf` において Chapter 1 以降が消失する。原因は `DEBUG_MAX_CHAPTERS` による制限および TOC 抽出失敗によるノイズ章の分断。
  - **対策:** デバッグ制限の削除、TOC プロンプトの改善、およびヘッダー判定の厳格化。
- Chapter 7, 8 は正常に残っている。

**原因特定**:
1. **Pass 1 (pdf_ingester.py)**: `ignored_patterns` によるフィルタリングが、ブロックの位置（座標）を考慮せずグローバルに適用されていたため、柱と類似したテキストを目次中央でも削除していた。（潜在的要因）
2. **Phase 1 (phase1_preprocess.py)**: `_RUNNING_HEADER_RE` が `^.{10,55}\s\d{1,3}$` という広いパターンを持っており、Chapter 1-6（長さ 30〜40 文字）がこれに合致して削除されていた。Chapter 7, 8 は 60 文字以上あったため、偶然この正規表現を回避していた。

**解決策**:
1. **`core/pdf_ingester.py`**: `extract_text_fast` 内で、`ignored_patterns` を適用する前に「ブロックがページの上部 15% または下部 15% に位置するか」を判定する座標制約（Position Constraint）を追加。
2. **`core/phase1_preprocess.py`**: `_RUNNING_HEADER_RE` にネガティブ・ルックアヘッド `(?!...)` を追加し、`Chapter`, `Part`, `Contents` 等の重要キーワードで始まる行を削除対象から除外。

**再発防止**:
- 座標を伴う抽出時（Phase 0）は、コンテンツの性質（中央か辺縁か）を常に考慮する。
- 文脈に依存しない汎用的な正規表現による行削除は避け、特定のキーワード（セクション名）を保護リストに加える。
1. **`core/pdf_ingester.py`**: `extract_text_fast` 内で、`ignored_patterns` を適用する前に「ブロックがページの上部 15% または下部 15% に位置するか」を判定する座標制約（Position Constraint）を追加。
2. **`core/phase1_preprocess.py`**: `_RUNNING_HEADER_RE` にネガティブ・ルックアヘッド `(?!...)` を追加し、`Chapter`, `Part`, `Contents` 等の重要キーワードで始まる行を削除対象から除外。

**再発防止**:
- 座標を伴う抽出時（Phase 0）は、コンテンツの性質（中央か辺縁か）を常に考慮する。

## 2026-03-17: 柱除去後の不要な空行の発生

**事慶**:
- `remove_inline_running_headers` で独立行のヘッダーを削除した際、削除した跡が空行として残り、元からある空行と重なって二重の空行が発生していた。

**原因特定**:
- 削除した行を `""` (空文字) に置き換えていたが、最終的な結合処理 `line.strip() or not line` が `""` を「維持すべき空行」と判定して出力に含めていたため。

**解決策**:
- `header_removed` フラグを導入。独立行ヘッダー検出時はリストへの `append` そのものをスキップするロジックに変更。

## 2026-03-17: 構造化時の [Unlabeled Section] 発生

**事象**:
- Book Mode において、LLM が生成したセクション見出しが原文とマッチせず、全ての段落が `[Unlabeled Section]` というダミー見出しの下に格納されてしまう。

**原因特定**:
- `normalize_heading` の正規表現が `Chapter` 以外の接頭辞（`Part`, `Section`, `Appendix`）や、アルファベット1文字のラベル（`Appendix A`）に対応していなかったため、正規化結果が食い違っていた。

**解決策**:
- `normalize_heading` の正規表現を拡張し、`Part`, `Section`, `Appendix` および `[A-Z]\b` ラベルをサポート。
- Phase 4 の `process_section` 内に、`[Unlabeled Section]` を自動で展開してフラットにするフォールバック処理を実装済み。
- **検証実績**: `psdpdf_p2.md` (9,188行) の全域において、`grep` 検索により `[Unlabeled Section]` が 0 件であることを確認。

## 2026-03-18: Route C (Full VLM) における構造の崩れ

**事象**:
- `pdf_mode="full_vlm"` で実行時、Phase 3 では完璧に構造化されているにもかかわらず、Phase 4 の翻訳後に見出しが消失したり、本文の一部（固有名詞など）が `####` 見出しに誤変換される。

**原因特定**:
- Phase 4 の `process_section` が、書籍モードにおいて「AIレジュメから見出しを再抽出して章内を分割する」という Route A/B 用のロジックを無条件で実行していた。
- VLM が出力した正確な原文見出しと、AIレジュメが生成した「まとめた見出し」が一致せず、マッチングに失敗して構造が破壊される挙動が発生。

**解決策**:
- **`core/phase4_translate.py`**: `pdf_mode == "full_vlm"` の場合は Phase 4 での再構造化を完全にスキップし、Phase 3 の TreeNode 木構造をそのまま信頼して翻訳ループに回すよう分岐を追加。

**再発防止**:
- 「構造化済みデータ」を入力とするフェーズでは、入力元の信頼度（VLMかPythonか）を確認し、多重の構造化による干渉を防ぐ。

## 2026-03-18: 書籍モードにおける意図せぬ Hybrid 動作

**事象**:
- 書籍（`--book`）で Clean な PDF を読み込んでも、1ページ目だけ VLM が呼ばれる、あるいは途中のページで VLM フォールバックが発生し、処理が低速化する。

**原因特定**:
- `pdf_ingester.py` の `run_pdf_ingestion_async` 内のルーティング判定が、書籍モード時も `should_use_vlm()`（論文用の Hybrid 判定）を呼び出していた。

**解決策**:
- 書籍モード判定を最上位に置き、`pdf_mode != "full_vlm"` ならば強制的に Python ルート（`extract_text_fast`）のみを通るように Bipolar 分岐を厳格化。

**再発防止**:
- モードによって「ページ単位の最適化（Hybrid）」か「ドキュメント単位の一貫性（Bipolar）」かを明確に分け、判定関数を共通化しすぎない。

## 2026-03-18: Route C での章タイトル誤降格 (Chapter 1 -> h3)

**事象**:
- Route C（Full VLM）において、Chapter 1 などの主要な章タイトルが `# `（h1/h2 相当）ではなく `### `（h3）に誤って降格されたり、逆に「柱」が章として誤認される。

**原因特定**:
- VLM はチャンク単位で処理するため、全体の目次（TOC）構造を把握できず、一貫した階層付けが困難。
- 以前の Python 側の `normalize_heading` が "Chapter 1" などのプレフィックスを過剰に削除していたため、照合精度が低下していた。

**解決策**:
- **TOCベースの2パス構造化**: 
    1. 全チャンクから `# ` で示された見出しを一通り集め、そこから「目次らしいエントリー」を抽出して TOC セットを作成。
    2. 二周目の木構造構築時に、`# ` 見出しが TOC に存在するか正規化照合。存在しない場合は `h3` へ自動降格。
- **`normalize_heading` の簡素化**: 記号除去と小文字化のみに留め、"Chapter 1" などの文字列を保持することで照合の堅牢性を向上。

**再発防止**:
- チャンク化された情報を統合する際は、「全体観（目次）」を動的に生成してからのバリデーションを必須とする。

## 2026-03-19: 論文モードにおける「謎の内容（重複要約）」の混入

**事象**:
- [Phase 4] 論文モード（Paper Mode）の出力において、各セクションの日本語本文の冒頭に、本来レジュメに含まれるべき日本語要約が、セクションタイトル直後に繰り返し挿入されていた。
- `Prefigured_p2.md` の `[Unlabeled Section]` 等で顕著に発生。

**原因特定**:
- `core/phase4_translate.py` の `rebuild_translated_tree` 関数内で、`is_book` が `False` の場合（論文モード）に、`resume_nodes`（要約ノード）を無条件で `ja_node.children` の先頭に `insert(0, ...)` していた。これは旧仕様の残滓であり、現在の 3部構成（レジュメ／英語／日本語）では冗長なノードとなっていた。

**解決策**:
- **`core/phase4_translate.py`**: 論文モード（`not is_book`）のブランチにおいて、`resume_nodes` を本文ノードへ挿入するロジックを削除。

## 2026-03-19: 論文モードの見出しレベルの不整合

**事象**:
- `ideal_mdstructure.md` の規定に反し、英語本文内の見出しが `##` (H2)、日本語本文内の見出しが `#` (H1) で出力されていた。

**原因特定**:
- Phase 3 において、論文モードのセクション見出しに `role="h2"` が割り当てられていた。
- Phase 5 の `tree_to_markdown` では `role="h2"` を基準点（オフセット0）として `base_level` を加算するが、Paper Mode の `base_level` 設定が `base_level=1` (Jp) / `base_level=2` (En) となっていたため、それぞれレベル1 / レベル2として出力されていた。

**解決策**:
- **`core/phase5_export.py`**: 論文モード（`p2workflowy` モードかつ `not is_book`）の `base_level` を、英語本文では `3` (-> H3)、日本語本文では `2` (-> H2) に修正。

**再発防止**:
- `TreeNode` の `role` 定義（h1/h2/h3）と、各出力モードの `base_level` のマッピング表をドキュメント化し、フェーズ間の階層定義の食い違いを防止する。

- **2026-03-18: 論文冒頭の長いタイトルが見出し（Introduction等）に誤検知される問題**
  - **問題**: 30文字以上のタイトルが大文字小文字の混在を理由に見出し判定を通過し、結果として Abstract セクションに不要な構造（h2等）が発生していた。
  - **原因**: `normalize_heading` 内の正規化ロジックが、長い文字列に対しても見出しのプレフィックス（Chapter等）がない場合に本文（p）と判定する「閾値」が甘かった。
  - **解決策**:
    - **文字数比率チェックの導入**: 30文字以上の行において、大文字または小文字が極端に偏っていない（＝自然な文章である）場合は、本文として扱うようガードを強化。
    - **Abstract前処理（先行退避）**: 最初の正規の見出しが出現するまでの全テキストを `[Unlabeled Section]` ノードとして一括確保するロジックを `structure_nodes_by_headings` に実装。これにより、タイトルや著者情報が後続のセクションに「漏れ出す」ことを構造的に防止。
  - **再発防止**: 構造化コードの変更時は、必ず `Prefigured.txt` のような「重厚な冒頭部」を持つサンプルで回帰テストを行う。

## 2026-03-19: 「22xツール連続呼び出し」警告と task_boundary 認識不全

**事象**:
- AIエージェントが自律行動中に「220ツール連続呼び出し」等の極限状態のシステム警告を受け、パニック状態に陥った。
- その後、AIが自身でタスク状態を正常化しようと試み、`<task_boundary_tool{TaskName:..., Mode:...}>` というXMLタグ形式の文字列を、通常の応答テキスト内に直接出力してしまった（システム側に正規のタスク境界として認識されなかった）。

**原因特定**:
1. **ツール呼び出しのフェイルセーフ**: AIエージェントが、ユーザーに制御（応答）を返すことなくバックグラウンドでツール（`git log`, `view_file` 等）を異常な回数連続して実行したため、システムの「無限ループ防止機構（上限）」に抵触した。
2. **システムとテキストレイヤーの乖離**: システム（Antigravityフレームワーク）におけるツール呼び出しは、専用のAPIコール（JSON-RPC等）で行われる仕様である。AIが焦って「テキストとして」XMLタグ風にツール名や引数を出力しても、それはただの「発言」として処理され、タスク状態のオーバーライド（強制同期）にはならない。

**解決策**:
- この現象が起きた際は、一旦 `notify_user` を呼び出してユーザーに処理の制御を返し、タスクチャンクを区切ることでシステム側のツール実行カウンタをリセットする必要がある。

**再発防止**:
- 一度のタスク指示（例：過去のGit履歴からの抽出と比較）が長大になりすぎる場合は、途中で自発的に `notify_user` を行い、「ここまで調査しました。続けて良いですか？」と中間報告・承認を求める設計（チャンク化）を徹底する。
