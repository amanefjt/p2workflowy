# p2workflowy Model Optimization Guide

p2workflowy V3 における Gemini モデルの**ルーティング戦略・並列度とレート制御の設計・実測ベンチマーク**。

> [!IMPORTANT]
> Gemini API 自体のモデル一覧・`thinking_level` 仕様・無料枠のレート値・料金・廃止情報などの**共通知識は [`gemini_models.md`](gemini_models.md) を参照**。同ファイルは `~/Code/shared/` からの同期物で**直接編集禁止**。このファイルは p2workflowy 固有の運用情報（ルーティング・並列制御の実装・ベンチマーク）のみを扱う。

**読み方**: §1〜§2 が「現行の設計はこうなっている」、§3 が「なぜそうなっているか」、§4〜§5 が数値的な裏付け、§6 が「まだ確かめていないこと」、§7 が変更の年表。まず §1・§2 を読めば現在の挙動を一通り追える。

## 1. 現行のモデル構成とルーティング

### 1.1 モデル名の正本

`core/coreprompts.json` の以下のキーが正本（`@lru_cache` されるため変更後はプロセス再起動が必須）。

| キー | 現在値 |
|---|---|
| `DEFAULT_MODEL` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_FREE` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_FREE_POOL` | `["gemini-3.1-flash-lite", "gemini-3.5-flash-lite"]`（§2 のモデル軸ラウンドロビン対象） |
| `DEFAULT_MODEL_VLM` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_RESUME` | `gemini-3.6-flash` |

ドキュメントとコードが乖離している場合はコード側を優先し、このドキュメントを修正すること。

### 1.2 ハイブリッド構成（2026-07-11 決定、現行）

レジュメ生成（論文全体・書籍全体・章単位）のみ `DEFAULT_MODEL_RESUME`（`gemini-3.6-flash`）を使い、**翻訳を含むそれ以外の全フェーズは `DEFAULT_MODEL`（`gemini-3.1-flash-lite`）を使う**。GA 移行後の価格改定で Flash と Flash-Lite の価格差が約 6 倍に拡大したため、品質影響が大きいレジュメ生成のみ高モデルを残し、他は Lite に統一した（根拠: 2026-07-11 Stage 1 モデル A/B、NST 論文、Arm B 採用）。

`DEFAULT_MODEL_RESUME` は `TierManager` のティア追従の対象外（`core/llm_client.py::get_default_model("resume")`）。無料ティアへダウンシフトした場合でもレジュメ生成は常に `DEFAULT_MODEL_RESUME` で実行される。詳細は `docs/management/requirements_log.md`（2026-07-11 Stage 1 A/B）。

実態として、有料/無料ユーザー間で実行モデルが異なるのは**レジュメ生成（Phase 2）のみ**であり、翻訳を含むそれ以外のフェーズは有料・無料とも同じ Lite モデルで処理される。

### 1.3 後継モデルへ切替えたもの／切替えなかったもの

- **`DEFAULT_MODEL_RESUME` は `gemini-3.5-flash` → `gemini-3.6-flash` へ切替済み（2026-07-22）**: Rate Limit が新旧完全一致（`gemini_models.md` §4）、価格は出力 -17%（入力同額）という純粋な改善のため。
- **`DEFAULT_MODEL` / `DEFAULT_MODEL_FREE` / `DEFAULT_MODEL_VLM`（`gemini-3.1-flash-lite`）は後継 `gemini-3.5-flash-lite` へ切替えていない**: Rate Limit は一致するが価格が値上げ（入力+20%・出力+67%、`gemini_models.md` §5）で、コスト最優先というハイブリッド構成の設計意図と衝突するため。GA 化して間もなく廃止予定もないため、現状維持のリスクは小さいと判断。

> [!NOTE]
> **「無料枠だから値上げは関係ない」わけではない**: 無料ティアは従量課金が $0 なので、無料キーで叩く限り価格改定は影響しない（効くのは Rate Limit のみで、これは新旧完全一致）。ただし `DEFAULT_MODEL`（PAID tier 既定）と `DEFAULT_MODEL_VLM`（tier 分岐なしで常時参照、`core/llm_client.py:35-58`）は、管理者の `APP_ADMIN_PASSCODE` 経由やユーザー自身の有料キーなど**課金対象の有料キーで呼ばれた場合はそのまま実 billing に乗る**。`DEFAULT_MODEL_FREE` も無料キー専用ではなく、有料キーのまま `TierManager` が 429/503 でモデルだけダウンシフトした場合にも使われうる。したがって Lite 系の値上げは「無料キー由来のトラフィックには影響しないが、有料キーが絡む経路には影響する」というのが正確な理解であり、これが上記の現状維持判断の根拠。

> [!NOTE]
> **`gemini-3.5-flash`（旧 resume モデル）の単発リクエスト実効入力上限は公称値よりかなり低い（2026-07-13 実測、`troubleshooting_log.md` I-20）**: 実測で約 186,000〜187,000 tok（概ね 735,000 字前後）を超えると `400 INVALID_ARGUMENT` になる。ただし後続の実測（2026-07-21、`Naven.pdf` 746,470字/165,673tok で成功）により、文字/トークン比が文書によって 3.9〜4.5 程度ブレるため**文字数だけを閾値にした判定は不正確**であることも判明した（`core/phase2_meta.py::MAX_INPUT_CHARS` は代理指標に過ぎない）。書籍モードの Phase 0 全文スキャンは `core/book_manager.py::RESUME_MODEL_SAFE_CHAR_LIMIT`（60万字）超で `DEFAULT_MODEL` へフォールバックするガードで対処済み。この上限は `gemini-3.5-flash` での実測であり `gemini-3.6-flash` では未検証（ガード自体は保守的な値のためそのまま流用）。より頑健にするなら `count_tokens` 相当での実測判定への切替が望ましいが未実装（2026-07-21 指摘、対応は見送り）。

### 1.4 フェーズ別ルーティング表

| 処理フェーズ | 使用モデル | thinking | 設計意図 |
| :--- | :--- | :--- | :--- |
| **Phase 1 — PDF VLM / OCR** | `DEFAULT_MODEL_VLM` (Lite) | LOW | コスト・速度優先。大量の画像処理を並行するため Lite 固定 |
| **Phase 1 — テキスト構造解析** | `DEFAULT_MODEL_FREE` (Lite) | HIGH | 見出し抽出（TextStructureExtractor）。Lite でも精度十分 |
| **Phase 2 — レジュメ生成（論文/書籍全体/章）** | `DEFAULT_MODEL_RESUME` (Flash) | HIGH | ティア非追従。品質影響が大きいため無料モード下でも Flash を維持 |
| **Phase 2 — DNA / Keywords** | `DEFAULT_MODEL` (Lite) | HIGH | ハイブリッド構成によりレジュメ以外は Lite |
| **Phase 3 — 構造ツリー / TOC** | `DEFAULT_MODEL` (Lite) | HIGH | セクション境界の論理判断 |
| **Phase 4 — 翻訳** | `DEFAULT_MODEL`（Lite・通常）/ `DEFAULT_MODEL_FREE`（`--lite`／フォールバック時、同じく Lite） | HIGH | ハイブリッド構成により通常時も Lite。`--lite` 指定時や TierManager 発動時も同一モデル |

Phase 4 翻訳プロンプトの `{resume_content}` には論文モードでは論文レジュメ、書籍モードでは書籍全体レジュメ＋章レジュメが毎バッチ注入される（`core/phase4_translate.py::build_translation_context()`。2026-07-11 Stage 1 で配線、当初は「なし」だった）。

### 1.5 thinking_level のフェーズ別設定

| フェーズ | thinking_level | 変更可否 |
| :--- | :--- | :--- |
| Phase 1 VLM / OCR | `LOW`（ハードコード） | 不可。画像→テキスト変換に思考は不要でコスト増になるだけ |
| Phase 1 テキスト構造解析 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |
| Phase 2 DNA・要約・キーワード | `HIGH`（デフォルト） | `--thinking LOW` で変更可。品質低下リスクあり |
| Phase 3 構造ツリー | `HIGH`（ハードコード） | 不可。セクション境界判断の精度に直結 |
| Phase 4 翻訳 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |

`--thinking LOW` フラグはコスト削減・速度優先の実験用途向け。本番処理では `HIGH` を維持することを推奨。モデルごとの `thinking_level` デフォルト値・課金の仕様は `gemini_models.md` §3 を参照。

## 2. 並列度とレート制御の現行設計

1リクエストが「どこ（どのキー・どのモデル）に発行され」「どう発行間隔を制御され」「同時実行数がどう抑えられ」「429/503 にどう対応するか」を、発行順に沿って説明する。

### 2.1 前提: 「無料/有料」はキー（プロジェクト）の属性

`TierManager`（`core/llm_client.py`）が 429/503 検知時に行う「ダウンシフト」は使用モデルを Lite に切り替えるだけで、リクエスト先の API キー自体は変わらない。Gemini API の無料/有料枠は**キーが紐づく GCP プロジェクトの課金設定**で決まり、無料枠の RPM/RPD/TPM は**キー単位ではなくプロジェクト単位**（同一プロジェクトで複数キーを発行しても枠は増えない）。したがって枠を実質的に増やすには**別々の GCP プロジェクトでキーを発行する**必要がある（同一 Google アカウント内の複数プロジェクトで可、別アカウントは不要）。GCP のプロジェクト作成数にはアカウント単位のソフト上限があり、「無料枠を増やす目的での複数プロジェクト作成」は Google の監視対象になりうるという指摘もコミュニティ報告にある（軽いリスクとして記録するに留め、実装のブロッカーとはしない）。

### 2.2 レーン: キー × モデルの独立した枠

無料枠の Lite プール（`gemini-3.1-flash-lite` / `gemini-3.5-flash-lite`）は Rate Limit の値が一致するが、**使用量カウンターは独立**（`gemini_models.md` §4 実測）。同様に、別 GCP プロジェクトのキーはそれぞれ独立した枠を持つ。この「(API キー, モデル) の組み合わせ」を**レーン**と呼ぶ。

無料キー K 本 × Lite プール M モデルで **K×M レーン**あり、各レーンが独立した RPM/TPM/RPD 枠を持つ。現行構成（無料キー4本 `GEMINI_API_KEY_FREE_1`〜`_4` × Lite 2モデル）では **4×2 = 8 レーン ≒ 120RPM 相当**（Lite 無料枠は 15RPM/プロジェクト/モデル、`gemini_models.md` §4）。

- **レーン割り当て**: 通し番号 `i` に対して `key = keys[i % K]`, `model = models[(i // K) % M]`（`core/llm_client.py::pick_lane()`。以前は `ParallelTranslator`/`OCRManager` に重複実装していたが集約済み）。連続するリクエストが必ず別キーへ散り、K×M 回でちょうど全レーンを一巡する。
- **リミッタ**: 各レーンに独立した `AsyncLimiter`（1 req/4s ≒ 15RPM 相当、`get_free_pool_rate_limiters(api_key)`、`(tier, api_key, model)` でキーイング）。
- **適用条件**: **FREE tier かつユーザーがモデル未指定のときだけ**。PAID tier・ユーザーがモデル明示指定時は従来どおり単一キー/単一モデル/単一リミッタ（挙動変更なし）。無料キーが1本以下の環境ではキー軸が自然に無効化され、モデル軸（2レーン）だけのラウンドロビンにフォールバックする。
- **`model_pinned` / `key_pinned` フラグ**: `call_gemini`/`call_gemini_async`/`translate_batch` は「呼び出し元が明示した `model`/`api_key` を、リトライ時の `ModelRotator`/`KeyRotator` の自動切替対象から除外する」ためのフラグを持つ。ラウンドロビンで意図的に `pool[1]` や `free_2` を選んでも、これが無いと「現在の解決済みモデル/キー（`current()`）へ引き戻す」既存ロジックにより常に先頭へ戻されてしまい、分散が成立しない。**プロアクティブな負荷分散（ラウンドロビン）とリアクティブな 429 フォールバック（`ModelRotator`/`KeyRotator` の forward-only 切替）は役割が異なるため明示的に分離している** — 混ぜると「どのレーンが本当に枯渇しているのか」をカウンタが追えなくなり、1本のバッチの一時的な 429 でプロセス全体が有料キーに移ってしまう副作用が出るため。
- 実装箇所: `ParallelTranslator._pick_batch_target()`（Phase 4 翻訳バッチ単位）、`OCRManager._pick_page_target()`（Phase 1 VLM ページ単位）。

### 2.3 同時実行数の制御（セマフォ）

レーンのレートリミッタは「発行間隔の下限」を決めるだけで、**実際に何本のリクエストを同時に飛ばせるか**は別途セマフォで制御する。

| 対象 | 機構 | 既定値 | 制御単位 |
|---|---|---|---|
| Phase 4 翻訳 | `asyncio.Semaphore(max_concurrent_sections)`（`ParallelTranslator`） | `8`（`--concurrent`） | **セクション**単位（バッチ単位ではない） |
| Phase 1 VLM OCR | `asyncio.Semaphore(vlm_concurrency)`（`OCRManager`） | `20`（`VLM_SEMAPHORE_LIMIT`） | **ページ**単位 |

- **`--concurrent` は 8 のまま据え置き**: concurrent=16/24 に上げても改善せず、むしろ微増した（AL 論文、45s→50s→52s、§4）。`max_concurrent_sections` は「バッチ」ではなく「セクション」の同時実行数であり、AL 論文はセクションが9個しかないため 8 でほぼ上限に達している。**8 を超えても、セクション数がボトルネックになる文書では効果がない**（セクション数の多い文書では意味を持ちうるが実測範囲では利得を示せていない）。
- **`VLM_SEMAPHORE_LIMIT` は 10 → 20 に引き上げ済み（2026-07-26）**: 「1ページ1リクエスト」で同時実行数がそのまま効くため、18ページが 10 並列だと2ウェーブに割れていたのが 1ウェーブで流れるようになった（41s→31s、429ゼロ）。引き上げが安全になったのは §2.2 のレーン設計により FREE tier の各リクエストが必ずレーンごとの `AsyncLimiter` を通るようになり、発行レートの上限がセマフォではなくリミッタ側で担保されるようになったため（レーン導入前は「クライアント側レートリミッタが一切無い」状態でセマフォだけが唯一の抑制だったため、引き上げは危険だった）。`OCRManager.__init__(vlm_concurrency=...)` で上書き可能（省略時はクラス定数）。CLI フラグは未追加（調整ニーズが具体化していないため）。

### 2.4 429/503 への対応: レーン単位のクールダウン（circuit breaker）

`KeyRotator`/`ModelRotator`/`TierManager.downgrade()` はいずれも forward-only（一度切り替わったら二度と戻らない）。これは「一時的な RPM/TPM 超過（1分待てば回復）」と「恒久的な RPD 枯渇（その日は回復しない）」を区別しないため、無料キーが複数本ある構成では「一瞬の 429 で無料枠を何本分も無駄に捨てて有料キーへ落ちる」実害になる。これを解消するため `LaneCooldownRegistry`（`core/llm_client.py::lane_cooldown`）を導入し、**(api_key, model) 単位で「いつまで使用不可か」を記録**する。

- **プロセスグローバル + `threading.Lock`（意図的にスレッドローカルにしない）**: `TierManager`/`ModelRotator` は Web の並行パイプライン対応のため `threading.local()` だが、`lane_cooldown` は逆に「このキーのこのモデルは枯渇している」という事実をスレッド・章を跨いで共有すべきだという判断から、意図的にプロセスグローバルにしている。`(api_key, model)` でキーイングするため Web の別ユーザー（＝別キー）を誤って巻き込むこともない。
- **クールダウン秒数**: 429 のエラーボディ（`quotaMetric`/`quotaId`/`RetryInfo.retryDelay`）から分類する（`_classify_quota_violation()`）。
  - RPM/TPM 起因: 既定 **60秒**（`retryDelay` が取れれば 1〜120秒にクランプ。`retryDelay` は不正確という報告があるため回復スケールを大きく超える値は信用しない）。
  - RPD 起因: **次の太平洋時間深夜までの残り秒数を実計算**（下限1時間・上限24時間でクランプ）。
  - quotaMetric 不明（503含む）: 安全側で既定 **30秒**（本当にリソース枯渇かどうか自体が不確かなケースを含むため、長時間ふさぐより早めに再挑戦させる方が実害が小さい）。
- **可逆**: クールダウンが明ければそのレーンは自然に候補へ戻る。ラウンドロビン（`pick_lane()`）はクールダウン中のレーンを避け、`KeyRotator.best_available()` は「クールダウン中でないキーのうち最も優先度の高いもの」を選ぶ（forward-only の `advance()` 自体は既存テストが依存するため変更していない。`best_available()` を新設してリトライループはこちらを使う）。
- **全レーンがクールダウン中の場合**: `pick_lane()` は `None` を返し、呼び出し元はクールダウンを無視した従来どおりの割当てにフォールバックする（例外を投げない・処理を止めない。「新しい情報が無い以上、従来どおりの挙動に委ねるのが安全」という判断）。
- **TPM 起因 429 でのモデルローテーション可否**: `quotaId` に `PerModel` という文字列が確認できる場合に限りモデルローテーションを試す（`_is_model_scoped_quota()`）。確認できない場合は根拠のない前提を置かず、保守的にキー切替へ直行する。この分岐が必要になった経緯は §7 変更履歴（2026-07-26 訂正）を参照。

### 2.5 章並列（書籍モードのみ）

書籍モードの章ループ（`core/book_manager.py::BookManager.run()`）は `ThreadPoolExecutor` で並列化されている。§2.2 のレーン設計は「1つのパイプライン実行内で複数リクエストをキー×モデルへ分散する」前提のため、複数の章スレッドが同時に同じ `pool_keys()` を見てラウンドロビンすると、スレッドごとのレートリミッタ（`threading.local()`）が互いを認識できず同じレーンへ多重発行してしまう。これを避けるため、**各章スレッドは開始前に `key_rotator.restrict_to([自分に割り当てられたキー], ["free"])` を呼び、そのスレッドから見える `pool_keys()`/`current()` を1本に縮退させる**。章スレッド内部では引き続きモデル軸のラウンドロビン（2 Lite モデル）は効く。

- キー本数 K が章数 N より少ない場合に備え、キーを `queue.Queue` にプールし、章タスクが1本取り出して終わったら返す方式（「同時に同じキーを使う章は高々1つ」をキューの排他取得で構造的に保証）。
- 既定の並列度は **無料キー本数と処理対象章数（スキップ後）の小さい方**。`--book-concurrency` で明示指定可能（`1` は常に直列＝回帰時の逃げ道）。
- 章単位 resume のスキップ判定（`output_paths.json` 確認）は LLM を呼ばない安価な処理のため、並列投入前に直列で済ませる。
- `chapter_sessions` は `[None] * N` を用意し `run_one_chapter()` がインデックスへ直接書き込む（完了順に `append` すると本の並び順が崩れるため）。
- 1章あたりの VLM 同時実行数は `max(4, VLM_SEMAPHORE_LIMIT(20) // effective_concurrency)` に按分（複数章が同時にスキャン PDF の VLM ルートに入ると、ページ画像のメモリ量と API レート負荷が章並列数倍に積み上がるため）。下限4・按分係数とも実測に基づく最適値ではなく保守的な初期値。
- `lane_cooldown`（§2.4）はプロセスグローバルなので章スレッドを跨いで正しく共有される。他のスレッドローカル状態（`TierManager`/`ModelRotator`/レートリミッタキャッシュ、§7 2026-07-21）はいずれも章スレッド単位で独立しており矛盾しない。

**なぜ Web 版では無効なのか**: `server.py` は `key_rotator.configure()` を一切呼ばない（1リクエスト＝1キー、`WebKeyPool` による同時実行スロット制御。§2.6 参照）。章並列の有効化条件を `key_rotator.is_configured() and len(pool_keys()) >= 2` の一点に絞ってあるため、`configure()` を呼ばない Web 版では `is_configured()` が常に `False` になり、章並列は構造的に発火しない。CLI でも無料キーが1本以下の環境では同じ理由で常に完全直列にフォールバックする。

### 2.6 CLI と Web アプリのキー運用の違い

- **CLI**: `main.py` はデフォルトで無料キー（`GEMINI_API_KEY_FREE_1`〜`_4`）を使い、429/503 が続いた場合のみ最終手段として有料キー（`GEMINI_API_KEY`）に自動フォールバックする（`KeyRotator`、起動時に一度だけ `configure()`）。
- **Web アプリ**: `server.py::WebKeyPool`（無料キー最大5本 `GEMINI_API_KEY_WEB_1..5`）を同時実行スロットとして使う。あるキーが使用中の間は別のリクエストに別の空きキーを割り当て、空きが無ければ（6人目以降）待たせず即座に「混雑中」の失敗として記録する。管理者パスコード・ユーザー自身の API キー入力の経路はこのプールを介さず無制限に動く。
- **スレッドローカル化（2026-07-21）**: Web 側の各並行パイプラインは `asyncio.to_thread` でそれぞれ別スレッド・別イベントループで動くため、`_CLIENTS`（クライアントキャッシュ）・`_CACHED_LIMITERS`（レートリミッタキャッシュ）・`TierManager` の内部状態（`current_tier`/`was_downgraded`）・`ModelRotator` はいずれも `threading.local()` ベース。これにより、あるユーザーの処理開始が別の処理中ユーザーのキャッシュを消したり誤ったモデル階層に切り替えたりする競合が構造的に起こらない。`apply_tier_settings(tier, api_key=...)` はさらに `(tier, api_key)` でレートリミッタをキーイングする（CLI のキーローテーションが複数キーを跨ぐ際にキーごとに正しい残余レートを持たせるため）。
- **書籍モードの章ディレクトリ**（2026-07-21）: `state/book_sessions/<book>_<fp>/chapters_state/ch<N>/` に物理的に分離済み。`core/config.py::SessionState.MAX_STATE_SESSIONS=10` は `state/` 直下の全セッション横断のグローバル上限で、書籍モードが章ごとに `state/` 直下の独立ディレクトリを使っていると1冊処理するだけでこの上限を回してしまっていたため（`book_sessions/` は独自の `MAX_BOOK_SESSIONS=5` 管理下にあり、章が個別セッションとして誤カウントされない）。Web 側で複数ユーザーが並行実行すると、あるユーザーの完了処理が別ユーザーのセッションディレクトリを削除してしまう実害があったための修正（`troubleshooting_log.md` I-40 とも関連）。

## 3. 意図的にそうしている設計判断（トレードオフ）

### 3.1 Phase 4 のセクション内バッチは直列のままにする（2026-07-26、ユーザー決定）

**現状**: 節（セクション）は `asyncio.Semaphore(max_concurrent_sections=8)`（§2.3）で並列だが、**節の中のバッチは直列**。`ParallelTranslator.translate_section_chunks()` が各バッチに直前までの訳文をスライディングウィンドウとして渡している（`previous = prompt_builder_func(all_translated)`）ため、バッチ間に逐次依存がある。

**並列化すれば速くなる余地は実際にある**: 2026-07-26 の書籍実走行（`relationspdf.pdf` 3章）のログでバッチ分布を数えると、ある章では最大の節が8バッチ、他の11節は1〜2バッチと**極端に偏っていた**。節は並列に走るので Phase4 の所要時間は「最もバッチ数の多い節」でほぼ決まり、残りの節が終わった後はレーンが遊ぶ。巨大な節が1つある文書（学術書・論文では典型的）ほど、この遊びが大きい。

**それでも直列を維持する**。逐次の鎖を切るとバッチ境界で訳語・文体がぶれるため（例: "the field-site" が前半「調査地」・後半「フィールドサイト」）。本ツールの用途は Workflowy で読む対訳アウトラインであり、訳語の揺れは速度と引き換えにしてよい種類の劣化ではない、というのがユーザーの判断。

将来再検討する場合の参考（検討はしたが**現時点では採用しない**）:
- (a) バッチ数が閾値を超えた大きな節だけ並列化して影響範囲を限定する
- (b) 直前バッチの訳文の代わりに Phase 2 のレジュメと用語集（`global_glossary.csv`）を全バッチに配って逐次依存を切る
- (c) 並列訳の後に境界だけ整合パスをかける

### 3.2 Gemma を併用しない理由（2026-07-26 調査）

無料枠 Lite プールの併用モデル候補として Gemma 系も検討したが不採用。理由: (1) 出力速度が `gemini-3.5-flash-lite` の約1/9（34 vs 318 tok/s）で、ラウンドロビンに混ぜると遅いレーンが必ず最後に残る落伍者になる。(2) structured output の公式サポートが確認できず、Phase 2/3 で必須の JSON スキーマが使えない。(3) 無料枠専用モデルで Paid Tier が存在しない（有料フォールバック先が無い）。

### 3.3 プロアクティブな負荷分散とリアクティブな 429 フォールバックを分離する理由

§2.2 で導入した `model_pinned`/`key_pinned` フラグの設計思想。ラウンドロビン（プロアクティブ）と `ModelRotator`/`KeyRotator` の forward-only 切替（リアクティブ）を混在させると、(a) どのレーンが本当に枯渇しているのかをカウンタが追えなくなる、(b) 1本のバッチの一時的な 429 でプロセス全体が有料キーに移ってしまう（forward-only の不可逆性がラウンドロビン下では確率的に必ず起きる）。8レーン ≒ 120RPM を能動的に使い切る設計では、単一レーンの 429 は「枠切れ」ではなく「一時的な混雑」である可能性のほうが高いため、レーン単位で完結させるほうが合理的と判断した。

### 3.4 `--concurrent` を 8 から上げない理由

§2.3 のとおり `max_concurrent_sections` は「バッチ」ではなく「セクション」の同時実行数。AL 論文（9セクション）で 16/24 に上げても改善しなかった（45s→50s→52s）のは、セクション数がボトルネックになっているため整合的な結果。セクション数の多い文書では上げる余地がありうるが、実測範囲では利得を示せていない（§6 の未検証事項）。

### 3.5 文書内でのモデル切替を許容する理由

`ModelRotator`/`KeyRotator` は forward-only のため、大きな書籍等で無料枠の RPD が尽きた場合、同一文書の処理途中でモデル・キーが切り替わり訳文のトーンがわずかに変わりうる。現状は「単一レーンで RPD 枯渇＝そのまま失敗/停滞」であり、切替は「本来失敗していたケースを完走させる」場合にのみ発生するため、既存挙動に対する正味の劣化ではなく改善と判断し、ユーザー確認済みで許容している。

### 3.6 Web 版で章並列を無効にしている理由

§2.5 に記載のとおり、`key_rotator.is_configured()` が Web 版では常に `False`（`server.py` が `configure()` を呼ばないため）という条件だけで自然に無効化される設計にした。理由は、Web の並行処理（`asyncio.to_thread` による別スレッド）と書籍の章並列（別スレッド）を両方有効にすると、レートリミッタ・`TierManager`・`ModelRotator` がいずれも `threading.local()` ベースであるため、複数の章スレッドが同一キーの同一レーンを共有して「自分は15RPM使える」と多重に思い込み、429 が多発する構造的リスクがあるため。

### 3.7 採用しなかった検討（結論のみ）

- **バッチサイズ上限の拡大**（2026-07-10 試算）: スライディングウィンドウの拡大や Phase 2 レジュメの毎バッチ注入は、追加コストが 1本あたり $0.1〜0.25 程度に収まり入力トークンの headroom にも余裕があると分かったが、コストの支配項は出力（訳文＋thinking）でありバッチ入力量の増減は総コストへの影響が相対的に小さいという整理に留まり、具体的な変更は行わなかった（その後 2026-07-11 Stage 1/2 で `resume_content` の毎バッチ注入・スライディングウィンドウの拡大は別経路で実現済み。§1.4 参照）。
- **VLM の同時実行数をさらに引き上げる案**: §2.3 のとおり 10→20 で決着済み（429ゼロを確認）。それ以上の値は未検証。
- **クールダウンの half-open 段階的復帰**（古典的 circuit breaker パターン）: クールダウンが明けた瞬間に即座にフル復帰する単純な実装を採用し、half-open は採用しなかった。無料枠 API キー運用の規模では実装の複雑さに見合わないと判断したため。

| AL | FREE候補（9,000字/8ch） | 19 | 約91秒 | 0 |

### 5.1 AL論文（18ページ）1本あたりのAPI呼び出し数

### 5.2 単一 Lite モデル基準の処理能力見積り（2026-07-20 実測、8レーン化以前の基準）

> [!WARNING]
> 以下の見積りは**単一モデル・単一キー基準**（8レーン化＝§2.2 より前）の実測に基づく。8レーン化により RPM は理論上 8 倍（≒120RPM相当）まで拡張されているが、この見積り自体の更新は行っていない（§6 未検証事項）。現状より保守的な下限の目安として読むこと。

### 5.3 書籍モード（VLM）1冊あたりの概算（2026-07-24、単一モデル基準の外挿）

200ページ級の書籍1冊（VLMルート）を AL論文の実測値を章数分に外挿すると、合計API呼び出しは**〜450〜500回**（Phase1 VLM OCR 〜200回、Phase2〜20〜25回、Phase3〜10〜20回、Phase4〜200〜250回）。単一Liteモデルの無料RPD予算（〜1,000〜1,500）と比べると200ページ級1冊なら1日の枠内に収まる計算になる（8レーン化以降はさらに余裕がある想定だが未検証）。RPDが実際に詰まってくるのは、1日に複数冊処理する場合や500ページを超える大部の書籍を単独で処理する場合。

実運用では、RPD予算の枯渇よりも **Google側の瞬間的な混雑（503 UNAVAILABLE）** や、**同一書籍セッションへの多重起動によるキャッシュ競合**（`BookManager` にロック機構が無いため、前回のプロセスを止めずに再実行すると発生しうる）の方が体感の詰まりとして顕在化しやすい（2026-07-24 実例: 同一書籍に対し `main.py --book` プロセスが4つ同時起動していたことが判明）。

## 6. 未検証・既知の限界

- **8レーン化後の処理能力見積りが未更新**（§5.2/§5.3）。RPD/RPM の見積りは単一モデル基準の実測のままで、8レーン構成での再計測は行っていない。
- **実際に無料枠の RPM/TPM/RPD を意図的に枯渇させての実地検証は行っていない**。`retryDelay`/`quotaMetric` の抽出ロジックは google-genai SDK のソースコードを読んで構造的に機能するはずだと確認したが、実際に踏んだ 429 は書籍実走行中の TPM 起因1件のみ（§7 参照）で、RPM/RPD 起因の429やクールダウンの実挙動は未確認。
- **RPD クールダウンの日次リセット計算**（`_seconds_until_next_pacific_midnight()`）は太平洋時間深夜リセットという一般的な仕様説明からの推定で、p2workflowy の利用キーで直接確認したものではない。
- **RPM/RPD の `quotaId` 命名が TPM と同様に `PerModel` を含むかどうかは未確認**（実走行で発生したのは TPM 起因の429のみ）。
- **TPM 訂正後の実装で、モデルローテーションが実際に429を回復させるケースは未実測**（今回踏んだ TPM429 は訂正前の実装で発生しキー切替で回復した。訂正後のコードでこの429を再現してモデルローテーションが成功することの実地確認はできていない）。
- **書籍モードは3章限定でのみ実地検証**。1冊丸ごとの実走行、章数がキー本数（4本）を超えるケースでのキュープール運用、無料キー3本以上が同時に枯渇した場合のデッドロック的挙動、はいずれも未検証（設計上は `key_queue.get()` がブロックし他章のキー返却で再開するはずだが未確認）。
- **VLM同時実行数の按分式**（`max(4, 20 // effective_concurrency)`）は実測に基づく値ではなく保守的な仮説値。3章の実走行はいずれも Docling ルート（VLM不使用）だったため、この按分式自体は未検証。
- **書籍モードのピーク時メモリ使用量は未実測**。
- **`max_concurrent_sections` は章並列化に伴って調整していない**（1章あたり8のまま）。理論上は章並列×セクション並列で最大32同時リクエストになりうるが、8レーン設計は章あたり2レーンに縮退するため実際のバースト幅はそれよりずっと小さいと考えられる（3章並列の実走行で429/503の増加は観測されなかったが、試行回数が少なく確定的ではない）。
- **速度改善の実測はいずれも単発〜2回計測**で複数 trial での統計的検証は行っていない。Phase4 の所要時間は API 側のテールレイテンシ（単一リクエストが60〜144秒かかるスパイク）に強く左右されることを繰り返し観測している。
- **無料キー4本運用のリスク**: 無料枠拡張目的の複数 GCP プロジェクト作成は Google の監視対象になりうるというコミュニティ報告がある（ブロッカーとはしていない）。
- **クールダウンは half-open ではなく単純な即時フル復帰**（§3.7 で不採用の理由を記載）。クールダウン秒数（RPM/TPM=60秒、unknown=30秒）は今回新規に設計した値で実運用でのチューニング余地がある。
- **同一書籍の同時重複アップロード**: `BookManager.session_dir` は内容フィンガープリント基準で `task_id` に基づかないため、異なる2ユーザーがほぼ同時に同一書籍をアップロードすると競合書き込みの可能性が残る（Web版、対応保留）。
- **キーローテーションは429/503のみをトリガーにする**。無効・失効した無料キーは `max_retries` 回リトライして失敗し、有料キーへは切り替わらない。
