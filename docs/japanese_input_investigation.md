# 日本語の論文・本を入力にする（調査メモ）

2026-10-06 時点の調査メモ。**実装はしていない**。急ぎではなく、着手するときの出発点として残す。
「確認済み」はコードを読んで分かったこと、「未確認」は実物で試していないこと。

## 目的

日本語の学術論文・本（縦書きを含む）を渡して、英語と同じように「全体のレジュメ → 章・節ごとのレジュメ → 構造化」までを行い、Workflowy のワークフローに載せたい。

## すでにできていること

- **章ごとに分かれた日本語 Markdown の本**のレジュメ（本全体＋章別）：`scripts/resume_from_md.py`（2026-10-05、`requirements_log.md` 同日エントリ）。構造化はしない。OPML 起点なら Cultivator の `scripts/opml_to_library.py` で先に章 MD に分ける。
- 日本語縦書き・見開き PDF のテキスト化：`~/Code/gocr`（別プロジェクト）。

## 今の p2workflowy が日本語入力で通らない理由（確認済み）

p2workflowy は「英語入力 → 日本語出力」の前提で作られている。

| フェーズ | 日本語を入れたとき |
|---|---|
| 2 レジュメ（`SUMMARY_PROMPT_ronbun`） | 動くはず。ただし節見出しを「英語節タイトル」と指定しており、日本語見出しで出るかは未確認 |
| 3 構造化（`TEXT_STRUCTURE_EXTRACTION_PROMPT` ほか） | 抽出ルールの例が英語の標準節（Abstract, Introduction …）。「はじめに」「おわりに」「注」を拾えるかは未確認 |
| 3 除外（`EXCLUDE_SECTION_KEYWORDS`） | 英語のみ（references 等）。「参考文献」「謝辞」は除外されない |
| 4 翻訳（`TRANSLATION_PROMPT`） | 日本語→日本語になり無意味。飛ばす必要がある |
| 5 出力 | 「英語は親子ネスト・日本語は並列展開」の非対称階層が前提。日本語だけの入力には合わない |

PDF 経路の構造化は、目次・フォント・座標・VLM の論理判断を併用しており（`routing.py`、`docling_ingester.py`、`physical_ingester.py`、`ocr_manager.py`）、物理抽出は座標を横書き前提で使う。Docling が縦書き日本語で通るかは未確認。書籍の章分割（`PDFSplitter`、`TOC_EXTRACTION_PROMPT`）も日本語の目次形式で通るかは未確認。

## gocr から流用できそうなもの

- gocr のプロンプト（`processor/prompts.py`）は、すでに見出しを物理的な孤立（上下の余白＝Moat、縦書きで行が途中で切れる＝Break）から `# ` で抽出し、ノンブル・柱・脚注を除去し、前ページ末尾の文脈を引き継ぐ。**つまり gocr の出力は完全な平文ではなく、見出し候補の情報をある程度含む。**
- 見開きの分割（ノド検出）と一段組／二段組の判定（`processor/image_detector.py`）。p2workflowy 側にも `spread_splitter.py` があり、重複・統合の余地がある。
- 縦書きの扱いの知見は `~/Code/gocr/docs/management/`（`requirements_log.md`、`troubleshooting_log.md`）に蓄積されている。**着手時に最初に読む。**

流用は「外部を参照する」のではなく、必要な部分を p2workflowy に取り込む前提。

## 段階案

| 段階 | 内容 | 重さ |
|---|---|---|
| 0 試験 | 日本語論文（1段組・2段組）を gocr でテキスト化し、今の `main.py` に入れて、どこで壊れるかを記録する | 小 |
| 1 日本語テキスト版 | 翻訳を飛ばす／日本語の見出し抽出と除外語／レジュメの節見出しを日本語にする／日本語用の出力形式 | 中。`core/` に手を入れる。`golden-verification` が使える理想出力が日本語にはないので、まず参照用の理想出力を作る必要がある |
| 2 縦書き PDF 起点 | VLM 経路を縦書き対応にし、gocr の知見を移す。日本語の目次から章を分ける | 大・不確実 |

PDF の構造化精度は、英語でも「PDF 版が最高品質、テキスト版はそれより下」。日本語のテキスト版（段階 1）は精度が下がる前提で、Workflowy に載せたあとに人が直す運用を許容する。

## 決めてあること・未決のこと

- **出力形式（案、未承認）**：日本語の原文を節ごとに親子ネストで置き、各節にレジュメを付ける。「日本語並列展開」のブロックは作らない。
- **p2workflowy と独立にするか（未決）**：現時点の見立ては、**同じリポジトリの別モード**（`--lang ja` か別エントリ）にして、`llm_client.py`（キー選択・TierManager・429 対応）、Phase 2 のレジュメ生成、Phase 5 の出力基盤は共有する。違いが大きいのはフェーズ 3（見出し規則）・4（翻訳なし）・出力形式なので、そこだけ分ける。別プロジェクトにすると API キー管理・レート制限の仕組みを二重に持つことになる。段階 0 の結果で、共有できる量を見てから最終判断する。
- **評論・人文書の形式への慣れ（懸念）**：日本語の論文・評論は節の立て方が英語の IMRaD 形式と違う（「はじめに／1／2／おわりに」、注の位置、章立てのない評論など）。見出し規則はプロンプトの例を日本語の実物から作り直す必要があり、藤田さんの実物（論文・評論）で調整する前提。
