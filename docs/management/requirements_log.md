# 要望ログ (requirements_log.md)

## 2026-03-08: レジュメの Markdown レベル混同
- **事象**: `SUMMARY_PROMPT` で `# 3. 各セクションの展開` の下に原文見出しを書かせると、LLM が気を利かせて `##` にレベルを下げてしまい、Phase 3 で正しく H2 として認識されない。
- **原因**: Markdown 階層の深さを LLM が自動調整したため。
- **解決策**: プロンプト内で「上の節番号に関わらず、必ず `#` で記述し、インデントしないこと」を強く指示。
- **結果**: 意図通り `#` 為る大見出しが生成され、Phase 3 で 7 つのセクションが正常に分離された。

## 2026-03-08: 翻訳フェーズでの要素数不一致リトライ
- **事象**: Phase 4 の翻訳において、入力チャンク数と LLM からの出力配列数が一致しないエラーが散発。
- **原因**: 長文や複雑な論理展開を含むセクションにおいて、LLM がチャンクを結合して回答してしまう場合がある。
- **対策**: `phase4_translate.py` に詳細ログを導入し、不一致が発生した際にリトライ（最大 5 回）が行われることを可視化。
- **結果**: `NSTsample.txt` のテストにおいて、特定のセクションで 4 回目のリトライで成功することを確認。リトライ機能による頑健性を証明。

## 2026-03-08: 階層構造の保持と抽出
- **要望**: レジュメ（Resume）生成時に、大見出し（H2）だけでなく小見出し（H3）も明確に区別して出力し、それを後続の構造抽出フェーズで正しく認識・ネストしたい。
- **背景**: これまでは小見出しが本文（p）と同等に扱われてしまい、ドキュメントの論理構造が失われていた。
- **こだわり**:
    - LLMの出力に `# [Header]` と `## [Subheader]` を含める。
    - インデントや記号が含まれていても頑健に抽出できる正規表現を使用する。

## 2026-03-08: パフォーマンス・ボトルネックの真因特定（4つの診断ログ）
- **要望**: 翻訳の遅延が「JSON制約」によるものか「プロンプト解釈」によるものかを白黒はっきりさせるため、高度なメトリクスを導入したい。
- **指示の詳細**:
    1. **TTFT (Time To First Token)**: 最初の1文字が出るまでの時間。
    2. **TPS (Tokens Per Second)**: 生成開始後の秒間トークン数。
    3. **Token Usage**: 実際のトークン消費数（Prompt/Output）。
    4. **Raw Payload Dump**: 送信された全ペイロードのデバッグ出力。
- **結果**: `llm_client.py` にストリーミング計測ロジックを実装。`NSTsample.txt` の完全翻訳を通じて、TTFT が支配的な要因であることを特定した。

- **要件の再定義**:
    - 論文の論理構造と翻訳の整合性を維持するため、**「要約（Resume）をContextとして常にプロンプトに注入すること」を絶対的な必須要件** とする。
    - いかなる理由（トークン節約等）があっても、この要約を除外してはならない。
    - 動的用語集（Dynamic Glossary）についても、現在は手動辞書に限定されているため、AI抽出キーワードを含めるよう改善が必要。
