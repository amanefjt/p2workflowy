# Design: 語彙投入戦略の最適化

## 設計の背景
論文翻訳において、固有名詞や専門用語の整合性を保つために「用語集（Glossary）」の注入は必須である。しかし、語彙数が増えるとプロンプトサイズが肥大化し、Gemini API の応答開始時間（TTFT）に悪影響を与える懸念があった。

## 検討された戦略
1. **Baseline (Mode 0)**: 統合された全語彙（ユーザー辞書 + AI抽出）をすべての翻訳リクエストに含める。
2. **Dynamic Filtering (Mode 1)**: 処理対象のチャンク内に含まれる単語のみを、送信直前にキーワード検索で抽出して注入する。
3. **Global Filtering (Mode 2)**: 翻訳開始前に論文全体のテキストをスキャンし、論文内に一度でも登場する語彙のみに絞り込む。

## 採用された設計（Rationale）
実測の結果、**Mode 0 (Baseline)** を採用した。

### 採用理由
- **TTFT の優位性**: 意外にも、プロンプトサイズが最大の Mode 0 が最も高速な TTFT（平均 17.5s）を記録した。Mode 1/2 は前処理のオーバーヘッドや、LLM 側のキャッシュ効率低下により遅延が悪化した。
- **キャッシュ効率**: 同じ語彙（コンテキスト）を繰り返し送ることで、LLM 側のインプットキャッシュが有効に機能し、2回目以降のリクエストが高速化される。
- **堅牢性**: 前処理（キーワード検索）の漏れによる訳文の不整合リスクを完全に排除できる。

## 構成要素
1. **Glossary Merger**: `core/phase4_translate.py` にて、静的CSVとAI抽出JSONをマージ。重複時はユーザー辞書を優先。
2. **Metrics Tracker**: `core/llm_client.py` にて、ストリーミングレスポンスから `ttft`, `tps` を算出し CSV へ記録。
3. **Logic Consolidation**: 実験終了後、複雑なフィルタリング分岐を削除し、常にマージ済み語彙を渡すシンプルなパイプラインに一本化。
