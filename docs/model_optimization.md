# p2workflowy Model Optimization Guide

p2workflowy V3 における Gemini モデルの**ルーティング戦略と実測ベンチマーク**。

> [!IMPORTANT]
> Gemini API 自体のモデル一覧・thinking_level 仕様・無料枠・廃止情報などの**共通知識は [`gemini_models.md`](gemini_models.md) を参照**。このファイルは p2workflowy 固有の運用情報のみを扱う。

## 1. フェーズ別モデルルーティング

V3（Golden Rewrite）では用途別に**動的ルーティング**を採用。モデル名の実態値は `core/coreprompts.json` の以下 3 キーが正本：

| キー | 現在値 |
|---|---|
| `DEFAULT_MODEL` | `gemini-3.5-flash` |
| `DEFAULT_MODEL_FREE` | `gemini-3.1-flash-lite` |
| `DEFAULT_MODEL_VLM` | `gemini-3.1-flash-lite` |

ドキュメントとコードが乖離している場合はコード側を優先し、このドキュメントを修正すること。`@lru_cache` のため変更後はプロセス再起動が必須。

### フェーズ別ルーティング表

| 処理フェーズ | 使用モデル | thinking | 設計意図 |
| :--- | :--- | :--- | :--- |
| **Phase 1 — PDF VLM / OCR** | `DEFAULT_MODEL_VLM` (Lite) | LOW | コスト・速度優先。大量の画像処理を並行するため Lite 固定 |
| **Phase 1 — テキスト構造解析** | `DEFAULT_MODEL_FREE` (Lite) | HIGH | 見出し抽出（TextStructureExtractor）。Lite でも精度十分 |
| **Phase 2 — DNA / Resume / Keywords** | `DEFAULT_MODEL` (Flash) | HIGH | 品質主権。論文全体の構造と意味を決定づける最重要フェーズ |
| **Phase 3 — 構造ツリー / TOC** | `DEFAULT_MODEL` (Flash) | HIGH | Phase 2 と同じモデルを継承。セクション境界の論理判断 |
| **Phase 4 — 翻訳** | `DEFAULT_MODEL`（通常）/ `DEFAULT_MODEL_FREE`（`--lite` / フォールバック時） | HIGH | 通常は Flash、`--lite` 指定時や TierManager 発動時は Lite へ |

### thinking_level のフェーズ別設定

| フェーズ | thinking_level | 変更可否 |
| :--- | :--- | :--- |
| Phase 1 VLM / OCR | `LOW`（ハードコード） | 不可。画像→テキスト変換に思考は不要でコスト増になるだけ |
| Phase 1 テキスト構造解析 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |
| Phase 2 DNA・要約・キーワード | `HIGH`（デフォルト） | `--thinking LOW` で変更可。品質低下リスクあり |
| Phase 3 構造ツリー | `HIGH`（ハードコード） | 不可。セクション境界判断の精度に直結 |
| Phase 4 翻訳 | `HIGH`（デフォルト） | `--thinking LOW` で変更可 |

`--thinking LOW` フラグはコスト削減・速度優先の実験用途向け。本番処理では `HIGH` を維持することを推奨。

## 2. Phase 4 並列数の実測（2026-05-11）

AL 論文（18p / 9セクション / 17バッチ）で `concurrent = 1, 2, 4, 8` を各 2 回実行。

| concurrent | trial 1 | trial 2 | **平均** | avg TTFT | p90 TTFT | max TTFT |
|---|---|---|---|---|---|---|
| 1（直列） | 329s | 348s | **338.5s** | 14.5s | 20.6s | 22.5s |
| 2 | 221s | 302s | **261.4s** | 22.6s | 21.2s | 205.8s |
| **4（デフォルト）** | **119s** | **335s** | **226.8s** | 22.6s | 28.7s | 214.7s |
| 8 | 216s | 83s | **149.3s** | 21.6s | 24.3s | 212.7s |

### 判明した事実

- **「240s TTFT 問題」は定常現象ではなかった**。avg TTFT は 14〜31s であり、2026-04-04 の外れ値（障害 × Phase 1 分割バグの複合）に基づいた誤った前提だった。
- **直列化（concurrent=1）は有意に遅い**。2 回とも 329s・348s と安定して遅く、並列化の効果は確実に実証（concurrent=4 比で約 49% 遅い）。
- **concurrent=4 と 8 の優劣は各 2 回の計測では判断できない**。trial 間の振れ幅が 100s 以上ある。
- **分散の原因は API サーバー側の混雑**。concurrent を上げると「速いときはより速く、詰まるときはより詰まる」特性（concurrent=2/4/8 全てで max TTFT が 200s 超のスパイク）。

### 結論

**デフォルト `concurrent=4` を維持**。変更を正当化する統計的データがない限り 4 を採用する。「並列化によりスループットが向上する」が正しい説明（旧来の「240秒ストールを並列で相殺する」は不正確）。

> [!TIP]
> 直列化（`max_concurrent_sections = 1`）は約 50% スループット低下。デフォルトの 4 を維持すること。

## 3. AL論文ベースの処理能力試算

### AL論文（18ページ）1本あたりのコスト

#### テキスト入力ルート（`.txt`）

| フェーズ | 処理内容 | API呼び出し | 入力トークン | 出力トークン |
|---|---|---|---|---|
| Phase 1 | テキスト構造解析（TextStructureExtractor） | **1回** | 〜13,000 | 〜100 |
| Phase 2 | DNA抽出・要約・キーワード | 3回 | 〜53,000 | 〜4,000 |
| Phase 3 | 構造ツリー抽出 | 1〜2回 | 〜16,000 | 〜2,000 |
| Phase 4 | 翻訳バッチ（セクション数依存） | **9〜17回** ★ | 〜170,000 | 〜170,000 |
| **合計** | | **〜15〜23回** | **〜250,000** | **〜175,000** |

> ★ Phase 4 のバッチ数はセクション数と 1 セクションあたりの文字量で変動。AL論文（9セクション）では 17バッチ（2026-05-11 実測）。

#### デジタルPDF入力ルート（Docling 使用）

| フェーズ | 処理内容 | API呼び出し回数 | 備考 |
|---|---|---|---|
| Phase 1 | Docling（ローカル処理） | **0回** | API コールなし |
| Phase 2〜4 | テキスト入力と同じ | — | — |

#### スキャンPDF入力ルート（VLM OCR）

Phase 1 で画像1枚ごとに VLM API を呼び出すため、ページ数に比例してコストが増大（18p で数十回規模）。

### ユーザー種別による動作

```
有料ユーザー:
  全フェーズ → DEFAULT_MODEL（高品質モデル）で処理

無料ユーザー（TierManagerの自動制御）:
  初回〜数回 → DEFAULT_MODEL を試みる
       ↓  429 RESOURCE_EXHAUSTED 発生（Flash の無料枠は早期に枯渇）
  残り全体 → DEFAULT_MODEL_FREE (Lite) へ自動ダウングレード
```

実態として、**無料ユーザーは 1 論文の処理中に TierManager が発動し、以降の全処理が Lite モデルで実行される**。品質は下がるが完走は保証される設計。

### 処理能力の目安（無料枠基準）

| ユーザー種別 | 実質動作モデル | ボトルネック | 1日 | 1ヶ月（30日） |
|---|---|---|---|---|
| **無料ユーザー** | Flash → Lite 自動切替 | Flash の RPD（数回で Lite へ） | **〜90〜130本** | **〜2,700〜3,900本** |
| **有料ユーザー** | Flash 固定 | TPM / RPM | 実質無制限 | 実質無制限 |

> 無料ユーザーは Lite の RPD（〜1,500）÷ 11 リクエスト ≈ 136 本/日が上限。最初の数回は Flash 品質で処理される。

### 処理速度（Phase 4 翻訳）

AL論文（9セクション / 17バッチ）、`concurrent=4`（2026-05-11 実測）：

| 条件 | Phase 4 完走時間 |
|---|---|
| 有料 + Flash、concurrent=4 | 119s〜335s（平均 227s / 約4分） |
| 無料 + Lite（フォールバック後） | 同等（モデル間の処理時間差は小さい） |

Flash と Lite の処理時間差はほぼない。**品質差**（文脈の深さ・訳の正確さ）が主な違い。

### 5.2 Phase 4 翻訳プロンプトの現状収支（1 バッチ）

バッチ構成の決まり方（`core/engine/p4_translate/parallel_translator.py` + `core/llm_client.py::apply_tier_settings`）:

| ティア | 最大チャンク数/バッチ | 最大文字数/バッチ（英語原文） |
|---|---|---|
| PAID（デフォルト） | 10 | 11,000 |
| FREE | 5 | 6,000 |

プロンプトの構成要素と実測サイズ。実測値は `state/` に残る Phase 4 デバッグプロンプト 57 件（AL 論文ほか、論文モード・PAID ティア）の文字数分布に基づく:

| 構成要素 | 内容 | 実測（文字） | 理論上限（文字） |
|---|---|---|---|
| テンプレート固定部 | `TRANSLATION_PROMPT`（日本語、指示・訳例） | 約 1,350 | 同左 |
| `resume_content` | **論文モードでは常に「なし」**（書籍モードのみセクションレジュメを注入） | 2 | 書籍モード: 数千字規模 |
| `glossary` | DNA キーワード 11〜12 件（`data/glossary.csv` は現状不在） | 299〜535 | 用語数に比例 |
| `previous_translation` | スライディングウィンドウ: 直近 **3 件 × 200 字**（日本語） | ≤ 628 | 約 630 |
| `source_chunks` | 英語原文 + `<p2w_chunk_ID>` タグ | 中央値 2,744 / 最大 7,543 | 約 11,300（タグ込） |
| **合計** | | **中央値 4,829 / 最大 9,192** | **約 13,900** |

セクション境界でバッチが切れるため、実測では 11,000 字の上限に達するバッチはまれ（最大でも約 7,500 字）である点に注意。

**トークン換算**（粗い目安: 英語 ≒ 4 文字/トークン、日本語 ≒ 1〜1.5 文字/トークン。正確な値は `count_tokens` API でのみ確定する）:

| ケース | 英語部 | 日本語部 | 入力トークン概算 |
|---|---|---|---|
| 実測中央値バッチ | 約 2,700 字 → 約 700 tok | 約 2,100 字 → 1,400〜2,100 tok | **約 2,100〜2,800 tok** |
| 理論最大バッチ | 約 11,300 字 → 約 2,800 tok | 約 2,600 字 → 1,700〜2,600 tok | **約 4,500〜5,400 tok** |

**headroom**:

- **入力**: 理論最大バッチでも入力上限 1,048,576 tok の **約 0.5%**（約 200 倍の余裕）。入力側の制約は事実上存在しない。
- **出力**: 11,000 字の英文の日本語訳はおおむね 9,000〜13,000 字 ≒ 6,000〜13,000 tok。これに thinking トークン（HIGH）が加算される。パース側の安全弁（1 チャンク 3,000 字 × 10 = 最大 30,000 字 ≒ 2〜3 万 tok）を想定しても出力上限 65,536 tok の半分以下であり、余裕はあるが入力側ほど桁違いではない。
- **コスト構造**: 3.5-flash・最大バッチで入力 ≈ $0.008、出力（訳文 + thinking で 1 万 tok と仮定）≈ $0.09。**現行単価では出力（thinking 込み）がコストの支配項**であり、入力側の増減はコスト全体への影響が相対的に小さい。

### 5.3 拡大シナリオの試算

基準: AL 論文（9 セクション / 17 バッチ）、`gemini-3.5-flash`（$1.50/1M 入力）。日本語 1 字 ≒ 0.7〜1 tok の目安で換算。

#### (a) スライディングウィンドウの拡大（現状 3 件 × 200 字 → 例: 10 件 × 500 字）

- 注入量: 約 600 字 → 約 5,000 字（差分 +4,400 字 ≒ **+2,900〜4,400 tok/バッチ**）
- 論文 1 本（17 バッチ）: **+5〜7.5 万 tok** → 追加コスト **約 $0.07〜0.11/本**（Lite なら 1/6）
- 入力 headroom への影響: バッチ入力が約 5 千 → 約 1 万 tok になる程度で、上限の 1% 未満。無視できる。

#### (b) レジュメの毎バッチ注入（Phase 2 `resume_content`、実測 5,225〜5,903 字）

現状、Phase 2 が生成する文献全体レジュメは論文モードの翻訳プロンプトには**注入されていない**（`resume_content` は「なし」）。これを毎バッチ注入した場合:

- 注入量: 約 5,500 字 ≒ **+3,700〜5,500 tok/バッチ**
- 論文 1 本（17 バッチ）: **+6〜9.5 万 tok** → 追加コスト **約 $0.09〜0.14/本**（Lite なら 1/6）
- §3 の現状試算（1 本の総入力 ≈ 25 万 tok）に対して **+25〜38%** の入力増に相当

#### (c) (a)+(b) 同時適用

- バッチ入力は約 5 千 → 約 1.4 万 tok（約 2.8 倍）だが、入力上限の **1.4% 未満**でトークン上限上の支障はない。
- 追加コストは合算で **約 $0.16〜0.25/本**（3.5-flash）。出力側（訳文 + thinking）のコストは変わらないため、1 本あたり総コストへの影響は限定的。

> [!NOTE]
> レジュメ・glossary・テンプレート固定部は同一文献内の全バッチで不変のため、注入量を増やす場合はコンテキストキャッシュ（$0.15/1M、通常入力の 1/10）の適用余地がある。ただし最小キャッシュサイズ等の条件は別途要確認。ここでは事実の記載に留め、採否の判断は別スペックで行う。
