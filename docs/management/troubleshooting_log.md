# トラブルシューティングログ (troubleshooting_log.md)

## 2026-03-08: 小見出し（H3）が抽出されない
- **事象**: `phase3_structure.py` の `extract_headings_from_resume` で、`##` から始まる小見出しが抽出されず、本文として扱われた。
- **原因**: 
    1. `SUMMARY_PROMPT` で見出しのレベル分けが明示されていなかった。
    2. 正規表現が厳格すぎ、冒頭のスペースや、見出しテキスト内の記号（引用符等）にマッチしなかった。
- **解決策**: 
    - `coreprompts.json` のプロンプトを修正し、`#` と `##` の使い分けを指示。
    - `extract_headings_from_resume` の正規表現を `r"^(#{1,2})\s+\[(.*?)\]$"` などに緩和。
- **再発防止策**: 見出し抽出ロジックには `line.strip()` を適用し、インデントの影響を排除する。

## 2026-03-08: Phase 2 の入力文字数が異常に少ない
- **事象**: `NSTsample.txt` (約67KB) を入力したが、Phase 2 のログで `(入力: 251 文字)` と表示された。
- **原因**: Phase 1 (`phase1_clean.json`) の状態ファイルに、過去のテスト用ダミーデータが残ったまま、フェーズがスキップ（または再開）されていた。
- **解決策**: `python3 main.py ... --resume 1` で Phase 1 から正しく実行し直す。
- **教訓**: `--resume` フラグを使用する際は、先行するフェーズの状態ファイルが最新の入力内容と一致しているか確認が必要。

- **解決策**: 作業内容をアーカイブした上で、以前の安定版 (`archive/stable_20260308_phase4_fixed/`) にロールバックし、`state/` を初期化した。

## 2026-03-08: レジュメの Markdown レベル混同
- **事象**: `SUMMARY_PROMPT` で `# 3. 各セクションの展開` の下に原文見出しを書かせると、LLM が気を利かせて `##` にレベルを下げてしまい、Phase 3 で正しく H2 として認識されない。
- **原因**: Markdown 階層の深さを LLM が自動調整したため。
- **解決策**: プロンプト内で「上の節番号に関わらず、必ず `#` で記述し、インデントしないこと」を強く指示。
- **結果**: 意図通り `#` 為る大見出しが生成され、Phase 3 で 7 つのセクションが正常に分離された。

## 2026-03-08: 翻訳処理の遅延原因の特定（TTFTボトルネック）
- **事象**: `Phase 4` の翻訳処理において、バッチごとの処理時間が 30秒〜1分程度かかり、全体として遅延が目立っていた。
- **原因**: 高度な診断ログ（TTFT, TPS等）の結果、以下の事実が判明した。
    1. **TTFT (Time To First Token) の高さ**: 最初の 1文字が返ってくるまでに 15s 〜 30s 以上の待機が発生している。
    2. **TPS (Tokens Per Second) の良好さ**: 生成開始後の速度は 200トークン/秒を超えており、JSON構造の複雑さはボトルネックではなかった。
    3. **結論**: プロンプトの解析（レジュメの読み込み）またはモデル自体の latency が支配的であり、出力フォーマットのせいではない。
- **対策**: `llm_client.py` に計測用プロファイリングログを常設。`gemini-3-flash-preview` 以外の低遅延モデルの検討を推奨。
- **教訓**: 「JSONのパースが遅い」といった推測に頼らず、TTFT と TPS を分離して計測することで、真のボトルネック（入力待機時間）を可視化することの重要性を再確認。

## 2026-03-08: API サーバーによる待機室（キュー）送りの解消
- **要望**: `Phase 4` において、並列数を上げようとすると TTFT (Time To First Token) が極端に悪化（250s超え）したり、タイムアウトが頻発したりした。
- **原因**: 短時間でのバースト的なリクエスト送信により Google API サーバー側で低優先度のキューに入れられていた可能性が高い。
- **解決策**:
    1. `semaphore = asyncio.Semaphore(1)` による完全直列化（一度に一セクションずつ）。
    2. `rate_limiter = AsyncLimiter(15, 60)` への設定戻し。
- **結果**: TTFT が 15s 〜 30s 程度で安定し、エラーなしで全 85 チャンクの翻訳を完遂。
- **教訓**: 無料枠や低ティアの API を使用する場合、並列度を上げるよりも「サーバーが拒絶しない程度の直列・定速処理」の方が、結果的に完了時間は短く、かつ安定する。

## 2026-03-09: response_schema (Structured Output) による突発的遅延
- **事象**: `Phase 4` において、特定の本文で TTFT が 280s を超える異常値が発生。
- **原因**: **Schema地雷。** `response_schema` を使用すると、API 側で重い制約計算リクエストと見なされ、確率的に低優先度キュー（5分間の待合室）に放り込まれる。
- **解決策**: 
    1. `response_schema` をコメントアウト。
    2. プロンプトでの指示を強化。
    3. JSON パース失敗時のための正規表現フォールバックを実装。
- **結果**: 同一の本文での TTFT が **284s → 16s** に改善。
- **教訓**: 性能と安定性が最優先のユースケースでは、API 側の Structured Output 機能に頼りすぎず、プロンプト制御とパース側の柔軟性で対応する方が「優先レーン」を維持しやすい。
## 2026-03-09: 共有APIキー機能の導入と撤回
- **事象**: 利便性のためにサーバー側で共有APIキーを保持する機能を検討したが、ユーザーの懸念により取りやめた。
- **解決策**: 実装済みの共通キーロジックを削除（ロールバック）し、各ユーザーが自身のAPIキーを `localStorage` に保存して利用する元の仕様を再徹底。
- **教訓**: コストと責任（API使用料）が伴う機能については、利便性よりも「透明性と納得感」を最優先すべき。

## 2026-03-09: UIの分離とメンテナンス性の低下リスク
- **事象**: `p2workflowy` と `RonbunNihongo` で HTML/JS ファイルが分かれたため、一方への修正（APIキーの注意書き追加等）をもう一方に反映し忘れるリスクが発生。
- **対策**: ファイルは分かれているが、共通の `style.css` を使用し、共通の JS ヘルパー関数（`pollStatus` 等）を定義することで、ロジックの乖離を最小限に抑えるよう配慮。
- **教訓**: UIの完全分離は「既存環境を壊さない」ための強力な手段だが、その後の変更作業は「常に2箇所」になるため、将来的なソースの共通化（コンポーネント化）の検討が必要。

## 2026-03-09: Phase 0 (PDF) 統合時の改行消失と設計上の葛藤
- **事象**: `pdfplumber` によるテキスト抽出を導入した結果、PDFの本来の段落区切り（空行）が消失し、Phase 1 の `smart_unwrap` が誤作動。
- **原因**: 決定論的な抽出コードでは、視覚的な空白と意味的な改行を区別できず、一律に「改行なし」のベタ打ちテキストに近い形式で出力されたため。
- **解決策**:
    1. Phase 1 に統計的な動的結合ロジックを導入しようとしたが、さらなる例外（見出しの消失など）を招くことが判明。
    2. **撤退（Rollback）の決定**: プロジェクトの目的を「翻訳と構造化の質」に絞るため、PDF直接読み込み機能を全面破棄。
    3. `git reset --hard` により GitHub 上の最新安定版に完全復旧。
- **教訓**: 上流工程（抽出）の不備を中流工程（整形）の複雑なコードで補完しようとするのはアンチパターン。「綺麗な入力（Word経由等）」を前提とする設計の価値を再認識。詳細は `docs/management/lessons_learned_pdf_integration.md` を参照。

## 2026-03-10: 語彙フィルタリングによる TTFT 悪化の特定
- **事象**: 翻訳速度向上のために導入した「動的語彙フィルタリング（Mode 1）」が、逆に TTFT を 10秒以上悪化させていた。
- **原因**: 
    1. Python 側でのキーワード検索（形態素解析等）の処理時間が、数千トークンの削減効果を上回っていた。
    2. プロンプトの内容がバッチごとに細かく変わるため、LLM 側のコンテキストキャッシュが効きにくくなっていた。
- **解決策**: 
    - フィルタリングを廃止し、マージ済みの全語彙を常にプロンプトに含める **Mode 0 (Baseline)** を採用。
- **結果**: TTFT が平均 28.6s から 17.5s へと大幅に改善。
- **教訓**: LLM の性能を最大限引き出すには、入力（プロンプト）の共通部分を最大化し、副作用のある「賢い前処理」を疑うことが重要。

## 2026-03-10: Gemini 2.0/2.5 Flash による PDF OCR の試行と撤退
- **事象**: Gemini 2.0/2.5 Flash (Vision) を用いた Phase 0 (OCR) を導入したが、出力結果の構造が不安定（重複、欠損、ノイズの混入）であり、実用レベルに達しないと判断した。
- **原因**: 
    1. VLM (Vision Language Model) による一括変換では、ページ間の重複排除や細かなページ下部ノイズ（Journal名等）の除去が困難。
    2. 入力 PDF のレイアウト複雑性に対し、一律のプロンプトで対応しきれず、テキスト処理パイプラインの下流（Phase 1-4）に悪影響を及ぼした。
- **解決策**: 
    1. **完全な原状回復 (Revert)**: `git restore` によりコードを安定版に戻し、`core/pdf_ingester.py` を削除。
    2. **方針の再定義**: PDF対応を本プロジェクトのスコープから再度除外し、「テキスト入力における絶対的な安定性と品質」を最優先する。
- **教訓**: 期待値の高い新機能（AI OCR等）でも、コア機能（翻訳・構造化）の信頼性を損なう可能性がある場合は、早期に切り離し、元の動作を保証することがプロジェクト全体の健全性につながる。
## 2026-03-10: Gemini API クォータエラー (429 RESOURCE_EXHAUSTED) の発生
- **事象**: `gemini-3-flash-preview` を使用中、API クォータ制限（Free Tier: 1日20リクエスト）に達し、処理が停止した。
- **原因**: 
    1. 使用モデル `gemini-3-flash-preview` の Free Tier 制限が非常に厳しいため。
    2. リトライロジックが 429 エラーに対して固定待機時間しか持っておらず、API 側が要求する「待機時間（数十秒）」に間に合わなかったため。
- **解決策**: 
    1. **モデルの使い分け**:
        - CLI版 (Python): 引き続き `gemini-3-flash-preview` を使用（高品質な出力を優先）。
        - Web版 (Render): 無料枠のリクエスト数制限が非常に緩い `gemini-3.1-flash-lite-preview` (500 RPD) を使用するように `server.py` を修正。以前の `2.5-flash` よりさらに安定。
    2. **動的待機リトライの実装**:
        - `llm_client.py` を修正し、エラーメッセージに含まれる `retry in X seconds` を正規表現で抽出。
        - 抽出された秒数分（+余裕1秒）自律的に待機してから再試行するロジックを同期/非同期の両方に実装。
- **結果**: 429 エラー発生時もクラッシュせず、API の指示に従って待機後に処理が継続されるようになった。
- **教訓**: 無料 API を商用に近い Web サービスで利用する場合、クォータの残量を意識したモデル選択と、API 側の「待機指示」を読み取れるインテリジェントなリトライロジックが不可欠である。

## 2026-03-11: Phase 3 における同名見出しのハッシュ（上書き）脱落バグ
- **事象**: `Technopdf.pdf` などを処理した際、長いセクション（本文）が Phase 3 で脱落し出力に含まれなかった。
- **原因**: 論文内で同名の見出し（例: "Technologies of the Imagination" が論文タイトルと章タイトルで重複）が出現した際、Python側 (`core/phase3_structure.py` の `build_tree`) で辞書 `sections_dict` のキー衝突が発生し、後から来た短い見出しチャンクにデータを上書きされていたため。テキスト・PDF問わず潜在していた致命的なバグ。
- **解決策**: 
    - `sections_dict` にキーを登録する際、既に同名キーが存在する場合は `(1)`, `(2)` のようにサフィックスを付与して一意にする自動連番ロジックを実装。
    - 子ノードの `current_node.text`（自身の見出し名）もそれに合わせて更新。
- **結果**: 脱落していた長文チャンクが正常に保持されるようになった。

## 2026-03-11: Webフロントエンドでの変数不整合（フォーム送信ロジックの脆弱性）
- **事象**: HTML側で「PDFをアップロードして」と注記を変更したものの、実態は `<textarea required>` のままでファイルインプットが存在せず、送信できない状態になっていた。
- **原因**: UIテキストのみを変更し、フォーム要素とバックエンドの受け口（Form引数）の連携を修正し忘れていたため。
- **解決策**:
    - フォームに `pdf_file` `<input type="file">` を追加し、textareaから `required` を外した。
    - JavaScript (`app.js`, `app_ronbun.js`) でテキストまたはPDFのいずれか一方が必須となるバリデーションを実装。
    - FastAPI (`server.py`) 側で `pdf_file: Optional[UploadFile]` を受け取り、分岐処理を行うよう修正。
- **教訓**: UIの文言修正を伴う仕様変更時は、常に「データの入り口から出口まで」の変数のリレーションを確認・デバッグする必要がある。
## 2026-03-11: 2段組論文での不自然なテキスト断片化
- **事象**: `SHORT_LINE_RATIO` による単純な短い行の改行判定を 2段組 PDF に適用すると、単語レベルでぶつ切りになり、翻訳結果が支離滅裂になる。
- **原因**: 1行の文字数が少ない 2段組では、段落の途中でも頻繁に短い行が発生し、それが「段落の終端」と誤認されるため。
- **解決策**: 改行判定に文末表現のチェックを追加。**「行が短く、かつ末尾が . / 。などの文末記号である」** 場合のみ改行（段落の分離）を行うようロジックを修正。
- **教訓**: レイアウトの物理的な特徴（長さ）だけでなく、意味的な特徴（句点）を組み合わせることで、ノイズの多い高速抽出でも実用的な段落保持が可能になる。

## 2026-03-11: 脚注番号によるページ跨ぎの誤結合
- **事象**: ページ末尾が `).4` などの脚注で終わる場合、次ページの先頭と結合されてしまい、構造解析が狂う。
- **原因**: ページを跨いだ文章の結合正規表現が、脚注の形式に対応しておらず、改行を不用意に削除していた。
- **解決策**: `core/pdf_ingester.py` の `re.sub(r'([^\s])\n([^\s])', ...)` マッチを調整し、脚注マーカーで終わる行を独立した行として維持。
- **結果**: ページ下部の注釈が次ページと混ざることなく分離され、セクション分割の精度が向上。

## 2026-03-11: Web 版プログレスバーのスタック（50%や75%で止まって見える）
- **事象**: 翻訳フェーズ（Phase 4）のように時間がかかる処理中、Web UI のプログレスバーが「分析中 (50%)」等から長時間動かず、フリーズしたように見える。
- **原因**: フロントエンドの `app.js` がフェーズごとに固定値を返しており、サーバー側の詳細なパーセンテージ更新を利用していなかった。
- **Result file not found (404) during download**:
    - **現象**: 処理が100%になり完了ボタンが出るが、クリックすると 404 エラーになる。
    - **原因**: `server.py` の `download` 関数が、PDFアップロード用ディレクトリ (`data/uploads`) だけを見て、実際に成果物が保存されている `state/` ディレクトリを見に行っていなかった。
    - **対策**: 両方のディレクトリを再帰的に（または優先順位を付けて）検索するように修正。
- **40% で Gemini 呼び出しエラー**:
    - **現象**: 分析開始時に API キーが無効であるとしてエラーが出る。
    - **原因**: 以前のテスト（DUMMY_KEY）がブラウザにキャッシュされ、それが優先的に送信されていた。
    - **対策**: `server.py` の入口でダミー文字列を検知して無視し、常に有効な環境変数のキーを使うようにガードを追加。
- **結果**: 翻訳中も 71%, 72%... と小刻みにバーが進むようになり、ユーザーの体感的な安心感を向上。
- **UnicodeDecodeError (docxやPDFをテキストとして処理)**:
    - **現象**: 処理開始直後に `UnicodeDecodeError: 'utf-8' codec can't decode...` というエラーで停止する。
    - **原因**: 拡張子が `.docx` や `.pdf` であっても、プログラムがそれを単純なテキストファイルと誤認して読み込もうとした（あるいは拡張子なしのバイナリを読み込んだ）。
    - **対策**: `core/pipeline.py` に `.docx` の自動検知抽出を追加し、さらに `phase1_preprocess.py` に例外処理を追加。バイナリと判明した場合は親切な誘導メッセージを出すように修正。
- **ダウンロードファイルに拡張子がない / 名前が UUID**:
    - **現象**: Macのダウンロード履歴で拡張子がなく、アイコンが白い汎用ファイルになる。
    - **原因**: サーバーのダウンロードURLの末尾がファイル名として誤認されたり、Content-Disposition ヘッダーが不足していた。
    - **対策**: `server.py` で `FileResponse` を返す際に `filename` 引数を明示。また `media_type` もファイルの拡張子に合わせて動的に設定するように強化。
