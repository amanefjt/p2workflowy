# 教訓レポート：PDF直接解析の試行と計画的撤退 (2026-03-09)

## 1. エグゼクティブ・サマリー

当初の「PDFから直接テキストを抽出してパイプラインに投入する（Phase 0の追加）」という試みは、技術的な複雑性の急増と、既存のクレンジングロジック（Phase 1）とのミスマッチを招き、最終的に「全面的な差し戻し」を選択しました。

本レポートでは、この過程で得られた技術的な洞察と、今後の開発における教訓を記録します。

## 2. 経緯

1.  **動機**: ユーザーの利便性向上のため、Word等を通さず直接PDFを読み込む `pdf_ingester.py` (Phase 0) を実装。
2.  **試行**: `pdfplumber` を用いた決定論的なレイアウト解析とテキスト抽出を採用。
3.  **発生した問題**: 抽出されたテキストに「空行」が含まれないため、Phase 1 の `smart_unwrap`（段落の再結合ロジック）が誤作動。1行1段落としてブツ切りになる現象が発生。
4.  **解決の試み**: Phase 1 側に「行の長さの中央値」を用いた動的な閾値判定などの高度なヒューリスティックを導入しようとした。
5.  **撤退の判断**: 上流（Phase 0）のノイズを下流（Phase 1）のヒューリスティックで解決しようとすると、例外処理が無限に膨らみ、システムの堅牢性が損なわれると判断。GitHub上の安定した「テキスト入力版」にロールバックした。

## 3. 技術的教訓

### ① 決定論的抽出の限界と「情報の欠落」
`pdfplumber` 等による決定論的な抽出は、座標情報を扱える一方で、人間が視覚的に認識している「段落の区切り（空行）」を正確に復元することが困難です。この「意味的な区切りの欠落」が、後続の `Smart Unwrap` エンジンの前提条件（空行が存在すること）を破壊しました。

### ② ヒューリスティックの泥沼（Heuristic Creep）
上流プロセス（PDF抽出）が生み出すノイズを解決するために、下流プロセス（Phase 1）に複雑な統計処理や例外リストを導入し始めると、コードの保守性が急速に低下します。「汚い入力には、まず人間がクレンジングした綺麗なデータ（Word経由のテキスト等）を与える」という V2 の当初の設計思想の正しさが再確認されました。

### ③ 「AI Vision OCR」対「決定論的コード」
決定論的なコードでPDFレイアウトを完全に解釈することは、学術論文の多様なフォーマットに対しては非効率です。もし直接PDFを扱うのであれば、今回検討したようなコードによる座標計算ではなく、Gemini Vision API 等の「視覚情報そのものを理解する AI」に OCR を任せる方が、結果的に下流のロジック（Phase 1）をシンプルに保てた可能性があります。

## 4. 戦略的教訓

*   **Git による迅速な復旧**: 複雑な機能追加（Phase 0）を行う前に、安定版を GitHub にコミットしていたことが命綱となりました。課題が「手に負えない複雑さ」に達した時点で、サンクコストを恐れず 1 命令でゼロに戻せたことは、プロジェクトの健全性維持において極めて重要でした。
*   **パイプラインの分離と契約（Contracts）**: フェーズ間の「データ形式の契約」がいかに重要かを痛感しました。Phase 1 は「空行のあるテキスト」を期待して設計されており、その前提（契約）を崩す入力を上流で作ってしまったことが失敗の本質でした。

## 5. 今後の指針

1.  **入力の単純化を維持**: 当面は「Wordから抽出したクリーンなテキスト（`.txt`）」を入力とする V2 の構成を維持し、翻訳精度と構造化の質を高めることに集中する。
2.  **PDF対応は慎重に**: もし将来的にPDFに再挑戦する場合は、最初から「Vision API 駆動の AI OCR」を採用し、人間が読むのと同等のクリーンな段落データを Phase 0 で生成することを目指す。
3.  **教訓の永続化**: このレポートの内容を `.agent/rules/` 等に反映し、将来の同様の「オーバーエンジニアリング」を未然に防ぐ。
