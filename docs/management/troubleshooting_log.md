# Troubleshooting Log

## 2026-03-15: Workflowy出力におけるフォーマット崩れ

### 事象
`relationspdf_p2.txt` の特定行（L455, L614等）において、Workflowyの形式（行頭の `- `）から外れる、または不自然な場所で箇条書きが分割される。

- **原因**: 1. `resume_to_workflowy` のインデント計算ロジック。2. チャンク間の不要な改行やタグの残留。
- **解決策**: `_sanitize_wf_text` 関数の導入と、インデントの `extra_depth` 制限（最大1階層）。
- **ステータス**: 解決済み (V2.7)

### V2.8: 大規模書籍における ID 衝突と構造崩れの予防（ベテラン監査パッチ）
- **事象**: 1,000段落を超える巨大な章がある場合、後続の章とノード ID が衝突し、翻訳が入れ替わったり消失したりするリスク。および、意訳による [Unlabeled Section] の残留。
- **原因**: `start_page * 1000` という固定オフセットの不足、および要約生成時のセマフォ保護欠如による RAM スパイク。
- **解決策**:
    1. オフセットを `10000` に拡大。
    2. 章レジュメ生成も翻訳用セマフォ (15並列) で保護。
    3. `[Unlabeled Section]` の階層を強制的に平坦化するクリーンアップ処理の強化。
- **ステータス**: 適用済み (V2.8)

### V2.9.2: API沈黙による「見かけ上のハング」とタイムアウト対策
- **事象**: 翻訳進捗が 89% 付近で停止し、数十分間ログが動かなくなる。プロセスは生存しているが、出力ファイルも生成されない。
- **原因**: 
    1. 特定の巨大な章（第2章など）の生成に、Gemini API 側で数分（最大 4.4分を確認）要していた。
    2. SDK のデフォルトではタイムアウトが設定されておらず、ネットワーク的に「迷子」になったリクエストを延々と待ち続けていた。
- **解決策**:
    1. `asyncio.wait_for(..., timeout=600)` による 1 リクエスト 10 分の強制タイムアウト導入。
    2. タイムアウト時の自動リトライ機能の実装。
    3. 全セクションの開始/終了ログと、バッチごとの進捗表示 (`Batch X/Y`) を追加し、無音時間を最小化。
- **ステータス**: 解決済み (V2.9.2)

### V2.9.7: 重複見出し (English text) の是正
- **事象**: `resume_only` モードにおいて、Workflowy 出力に `- English text` が二重に出現する。
- **原因**: 
    1. Phase 4 (`rebuild_translated_tree`) が構造維持のために `English text` という名のラッパーノードを作成していた。
    2. Phase 5 (`generate_resume_only_workflowy`) がエクスポート時に独自に見出しを出力していた。
    3. 両方が合わさり、見出し（Phase 5）の直下にさらなる見出し（Phase 4由来）が含まれる形となった。
- **解決策**: Phase 4 において `resume_only` 時のラッパー生成を廃止し、Phase 5 のプレゼンテーション層に一本化した。
- **ステータス**: 解決済み (V2.9.7)

### 2026-03-15: ショートカット実行時の「ファイルが見つかりません」エラー
- **事象**: `p2w` などのショートカットでパスを貼り付けた際、引用符 (`'` や `"`) が含まれていると、パス全体が正しく認識されずエラーになる。
- **原因**: zsh の `read` で取得した変数に引用符が文字として残ってしまい、`main.py` にそのまま渡されていた。
- **解決策**: エイリアス内で `${target%\"}` 等のパラメータ展開を用いて周囲の引用符を剥離する処理を追加。
- **ステータス**: 解決済み (V2.9.8)
### 2026-03-16: Phase 3 構造破損とメタキーワード判定の誤爆
- **事象**: 
    1. セキュリティパッチ適用時の置換操作ミスにより、`phase3_structure.py` の `re.sub` 周りに不要な URL や改行が混入し、シンタックスエラーが発生。
    2. 「構成と理論的貢献」等のメタキーワードが部分一致判定だったため、有効な章解説が除外されるリスクがあった。
- **原因**: 
    1. AIエージェントによる大規模置換時の微細なコンテキスト欠落。
    2. `any(k in title ...)` による緩い判定。
- **解決策**:
    1. 手動（または最小チャンク）によるコードクリーンアップと `py_compile` 検証。
    2. `normalize_heading` 後の値をセット (`meta_keywords`) と完全一致比較するように変更。
- **解決策**:
    1. 手動（または最小チャンク）によるコードクリーンアップと `py_compile` 検証向。
    2. `normalize_heading` 後の値をセット (`meta_keywords`) と完全一致比較するように変更。
- **ステータス**: 解決済み (V3.0.0)

### 2026-03-16: HF デプロイ後の "INVALID_ARGUMENT" (API Key) エラー

- **事象**: HuggingFace Spaces で「合言葉」を入力しても、Gemini API から「API key not valid」エラーが返される。
- **原因**: サーバー側（`server.py`）でパスコードを本物の管理者キーに置換するロジックの実装が漏れていた。
- **解決策**: `server.py` に `APP_ADMIN_PASSCODE` による API キー変換ロジックを追加し、管理者キーを透過的に使用可能にした。
- **ステータス**: 解決済み (V3.2.4)

### 2026-03-16: ストレージクリーンアップの不徹底

- **事象**: 古いタスクのエントリは削除されるが、ディスク上の物理ディレクトリが残り続け、HF のディスク制限に達するリスク。
- **原因**: `del task_status[tid]` のみを行っており、ファイルシステムの操作が行われていなかった。
- **解決策**: `shutil.rmtree` を使用し、`data/uploads/` および `state/` 内の該当 UUID ディレクトリを物理削除するロジックを追加。
- **ステータス**: 解決済み (V3.2.4)
