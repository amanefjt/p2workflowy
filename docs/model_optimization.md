# Gemini Model Optimization Guide (V3: Golden Rewrite Edition)

p2workflowy V3 における、各 Gemini モデルの最適化設定、運用ノウハウ、および API レート制限に対抗する「最適並列ペーシング」に関する最新の知見まとめ。

## 1. 推奨モデルとルーティング戦略

V3（Golden Rewrite）では、用途に応じたモデルの**動的ルーティング**を確立している。

| 処理フェーズ (用途) | 推奨モデル | ポリシー |
| :--- | :--- | :--- |
| **Phase 1 (VLM / OCR)** | `gemini-3.1-flash-lite-preview` | **コスト・速度優先**。大量の画像処理を並行して行うためLiteで十分。 |
| **Phase 2 (DNA / Resume)** | `gemini-3-flash-preview` (高品質) | **品質主権**。論文全体の構造と意味を決定づける最重要フェーズのため、基本は高品質モデルを使用。 |
| **Phase 4 (Translation)** | 動的選択 (Flash or Lite) | `--lite` 指定時やフォールバック時は `3.1-flash-lite`。それ以外（通常時）は `3-flash-preview` を使用し、文脈の深さを維持。 |

## 2. Thinking Level (思考レベル) の活用と罠

Gemini シリーズの `thinking_level: HIGH` は、学術論文のレジュメ生成や複雑な長文翻訳において絶大な効果（文脈推論の正確さ、JSON/XMLタグの維持）を発揮する。しかし、以下の強烈な副作用が存在する。

*   **「思考予算」の罠**: `Thinking: High` + 巨大コンテキスト（8万文字）の組み合わせは、Google API バックエンドで極めて重いタスクとして扱われる。これを同一キーで連続・並列送信すると、深刻なサーバー側での塩漬け（キューイング遅延）を引き起こす。

## 3. Phase 4 並列数の実測検証（2026-05-11）

AL 論文（18p / 9セクション / 17バッチ）で `concurrent = 1, 2, 4, 8` を各 2 回実行し、総時間と TTFT を計測した。

### 実測結果（2026-05-11、AL論文 17バッチ）

| concurrent | 総時間 trial 1 | 総時間 trial 2 | **総時間平均** | avg TTFT 平均 | p90 TTFT | max TTFT |
|---|---|---|---|---|---|---|
| 1 | 329s | 348s | **338.5s** | 14.5s | 20.6s | 22.5s |
| 2 | 221s | 302s | **261.4s** | 22.6s | 21.2s | 205.8s |
| 4 | 119s | 335s | **226.8s** | 22.6s | 28.7s | 214.7s |
| 8 | 216s | 83s | **149.3s** | 21.6s | 24.3s | 212.7s |

### 判明した事実

*   **「240s TTFT 問題」は定常現象ではなかった**。avg TTFT は 14〜31s であり、2026-04-04 の外れ値（障害 × Phase 1 分割バグの複合）に基づいた誤った前提だった。
*   **直列化（concurrent=1）は有意に遅い**。平均 338.5s は concurrent=4 の 226.8s に対して約 49% 遅く、並列化の効果は実証されている。
*   **concurrent=8 が平均最速**（149.3s）だが、trial 間の分散が非常に大きい（83s〜216s）。API サーバーの混雑状況に強く依存する。
*   **concurrent=4 はバランスが良いデフォルト**。最速ではないが、大きな外れを生みにくい。concurrent=8 への変更も合理的だが高分散を許容できる場合に限る。

### 結論：並列化の原則

直列化（concurrent=1）は避けるべきである。ただし「240秒ストールを並列で相殺する」という旧来の説明は不正確であり、**「同じ TTFT 環境下でも並列化によりスループットが向上する」** が正しい説明となる。

> [!TIP]
> **デフォルト値の根拠**: `max_concurrent_sections = 4` は安全で合理的なデフォルト。より高速化したい場合は `--concurrent 8` を試せるが、API の混雑時に総時間が跳ね上がるリスクがある。

## 4. API ティア管理とクラウド環境での自己修復 (Self-Healing)

Hugging Face Spaces や ローカル運用時において、API の上限到達によるクラッシュを防ぐため、V3 には強力な **TierManager (自律的ダウングレード機構)** が実装されている。

- **429 RESOURCE_EXHAUSTED の神回避**: 
  - 無料枠 (Free Tier) 等で `gemini-3-flash` のクォータ（例: 20 requests/day）を超過して 429 エラーが発生した場合、システムは全体をパニック終了させない。
  - **自動ダウングレード**: 即座に例外をキャッチし、軽量かつ制限の緩い `gemini-3.1-flash-lite-preview` へと内部状態を切り替え、そのまま次のリトライを実行する（**フォールバック**）。
  - この自己修復機能により、クラウドの過酷な環境でも処理を一度も取りこぼすことなく最終フェーズ（Markdown出力）まで到達（Production Ready）する。

## 5. 運用コストと実測パフォーマンス (2026-05 更新)

AL 論文（18p / 9セクション / 17バッチ）における Phase 4 実測値（2026-05-11）。

| concurrent | Phase 4 総時間（2回平均） | avg TTFT | 備考 |
| :--- | :--- | :--- | :--- |
| 1（直列）| 338.5s（約5.6分） | 14.5s | 安定だが最も遅い |
| 2 | 261.4s（約4.4分） | 22.6s | — |
| **4（デフォルト）** | **226.8s（約3.8分）** | **22.6s** | バランス良好 |
| 8 | 149.3s（約2.5分）| 21.6s | 最速だが高分散（83s〜216s）|

> モデル（Flash / Lite）による処理時間の差はほぼない。品質差（文脈の深さ）が主な違い。

> [!TIP]
> **直列化の回避**: 並列数（`max_concurrent_sections`）を 1（直列化）にするとスループットが約 50% 低下する（実測: 338s vs 227s）。デフォルト 4 のまま運用するか、高速化したい場合は `--concurrent 8` を試すこと。「240秒ストール問題」は 2026-04-04 の一時的な外れ値であり、現在の定常状態は avg TTFT 14〜31s である。

## 6. 無料/有料ユーザーの処理能力試算

### 前提：AL論文（18ページ）1本あたりのコスト

AL論文（Arbitrary Locations, 18ページ, 約61,000文字 / 124チャンク / 9セクション）を基準に計算。

| フェーズ | 処理内容 | API呼び出し回数 | 入力トークン | 出力トークン |
|---|---|---|---|---|
| Phase 1 | Docling（デジタルPDF → ローカル処理）| **0回** | 0 | 0 |
| Phase 2 | DNA抽出・要約・キーワード | 3回 | 〜13,000 | 〜1,500 |
| Phase 3 | 構造ツリー抽出 | 1〜2回 | 〜16,000 | 〜2,000 |
| Phase 4 | 翻訳バッチ（11,000文字 × 6バッチ）| 6回 | 〜21,000 | 〜21,000 |
| **合計** | | **〜11回** | **〜50,000** | **〜24,500** |

→ **1論文あたり 約75,000トークン・約11リクエスト**

> スキャンPDF（VLM OCRルート）の場合はPhase 1でも大量のAPIコールが発生するため、上記は「デジタルPDF」限定の数字。

---

### ユーザー種別によるモデル動作の違い

```
有料ユーザー:
  全フェーズ → gemini-3-flash-preview（高品質モデル）で処理

無料ユーザー（TierManagerの自動制御）:
  初回〜数回 → gemini-3-flash-preview を試みる
       ↓  429 RESOURCE_EXHAUSTED 発生（Flashの無料枠は早期に枯渇）
  残り全体 → gemini-3.1-flash-lite-preview へ自動ダウングレード
```

実態として、**無料ユーザーは1論文の処理中にTierManagerが発動し、以降の全処理がLiteモデルで実行される**。品質は下がるが完走は保証される設計。

### 処理能力の目安（AL論文 / 18ページ相当で換算）

#### Gemini API 無料枠の制限値（2025年12月改定後）

Googleは制限値を公式テーブルとして一切公開していない。以下はAI Studio / 公式ドキュメントから確認できる最新の参考値（**変動あり・要確認**）。

| モデル | RPM | RPD | TPM | TPD |
|---|---|---|---|---|
| gemini-3-flash-preview（Flash） | 〜15 | 〜250〜1,500 ※ | 〜250,000 | 非公開 |
| gemini-3.1-flash-lite-preview（Lite） | 〜30 | 〜1,000〜1,500 | 〜250,000〜1,000,000 | 非公開 |

> ※ 2025年12月の無料枠改定でFlashのRPDが大幅削減（一部報告では250/dayまで低下）。Liteは相対的に余裕がある。公式制限は [AI Studioダッシュボード](https://aistudio.google.com) で自プロジェクトの現在値を確認すること。

#### 1日・1ヶ月あたりの処理本数

| ユーザー種別 | 実質動作モデル | ボトルネック | 1日 | 1ヶ月（30日）|

| **無料ユーザー** | Flash → Lite自動切替 | FlashのRPD（数回でLiteへ移行） | **〜90〜130本** ★ | **〜2,700〜3,900本** |
| **有料ユーザー** | Flash固定 | TPM / RPM | 実質無制限（RPM=300） | 実質無制限 |

> ★ 無料ユーザーはLiteのRPD（〜1,500）÷ 11リクエスト ≈ 136本/日が上限。ただしFlash枠を使い切るまでの最初の数回はFlash品質で処理される。TPD非公開のため、実際にはTPM（トークン/分）の帯域が先に詰まる可能性もある。

| 条件 | Phase 4 完走時間 |

| 有料 + Flash | 約10分 |
| 無料 + Lite（フォールバック後）| 約9分半〜14分 |
